03 / 一句话架构

真实运行形态：Module Federation 远程加载 + micro-base 统一实例 + 主应用路由树合并

基座不是一个可见页面容器，它更像主子应用共同依赖的运行时内核。
Browser 进入 /scs 加载 vmi-admin-fe 静态资源
→
加载 microBaseEntry.js 获得 BootstrapApp / router / store / module API
→
加载子应用 remote scsProductPmsEntry.js / scmProductEntry.js
同一套 router/store/i18n 主子应用共享核心实例，避免多实例
→
注册业务路由与 store registerRouter / loadRouter / registerStore
→
侧边栏渲染菜单 registeredRoutes + 权限过滤
讲法：可以把它描述成“运行时组装”：远程代码先被加载，随后被基座注册进同一个 Vue 应用实例。

04 / 不是同一种微前端

这套链路和 PMS iframe 要分开讲，避免听众把两个机制混在一起

当前代码里确实存在 PMS iframe 预加载和嵌入，但它是 `/admin` Normal PMS 的特殊集成，不是 sbs-product-fe 的接入方式。
sbs-product-fe

Module Federation 子应用

  • 暴露 JS 模块：`./routes`、`./basic`、`./domains`
  • 主应用 import 后拿到路由、组件、领域能力
  • 最终渲染在同一套 Vue Router / Vuex 下
/admin PMS

iframe 嵌入系统

  • 通过 iframe 保留另一个系统自己的运行时
  • 有独立的预加载、postMessage、权限短路逻辑
  • 用于 Normal PMS 页面，不代表 product 子应用方案
一句话区分：Product 子应用是“代码模块进主应用运行时”；PMS iframe 是“另一个应用在 iframe 内独立运行”。

05 / 启动总线

BootstrapApp 把分散在主应用里的初始化过程收拢成稳定阶段

当前 micro-base 的 `BootstrapApp.run()` 是整个架构的主干：创建实例、加载模块、运行插件、合并菜单、挂载页面。
1
initCreate注册插件，创建 router、store、i18n，并触发 before/after create。
2
initModule进入 beforeModule/afterModule，主应用插件在这里注册 store 和 routes。
3
initPlugin执行插件 run，注入通用 SDK 或定制设置。
4
REGISTER_ROUTER + mounted构建 registeredRoutes 菜单树，再 `new Vue(...).$mount('#app')`。
// micro-base/src/bootstrap/runner/index.ts
async run() {
  await this.initCreate();
  await this.initModule();
  await this.initPlugin();
  store.dispatch('REGISTER_ROUTER');
  this.mounted();
  await this.triggerLifecycle('afterInit');
}

06 / 主应用接入

vmi-admin-fe 通过 bootstrapProps 和 BootstrapAppPlugin 注入项目差异

基座负责流程，主应用负责传入业务配置和在生命周期里注册自己的模块。这样“通用能力”和“项目差异”可以分层。

声明主应用身份与启动配置

  • `business: 'SCS'`、`portal: 'PMS'`、`region`

  • 插件列表：主应用插件、远程插件、LiveTip、QMS

BootstrapAppPlugin

在生命周期里注册项目模块

  • `beforeCreate` 执行 initAppSetting
  • `beforeModule` 注册本地 store、远程 user store
  • 加载 async routes，并把它们挂到 Root 下

讲法：主应用不再自己手写完整启动流程，而是“给基座一份配置 + 一个插件”，把业务差异挂到固定时机。

10 / 共享实例

router 和 store 用 Proxy 包一层，是为了让主子应用拿到同一套核心实例

这是解决多实例问题的关键。子应用 import `@retail/micro-base/core-instance` 时，拿到的是基座维护的单例代理。
Core Instance

router / store 单例代理

  • `createVueRouter` 创建一次后写入 globalData
  • `createVuexStore` 默认注入 `registerRouterStore`
  • Proxy 优先读 inner 实例，兜底读 globalData

Host Global Data

业务数据仍由主应用补齐

  • `window.__GLOBAL_DATA__` 里放 API、request、constants、Utils
  • 这是当前 product 子应用复用主应用能力的重要桥
  • 文档目标是进一步收敛到基座 Global Data

12 / 当前落地状态

和文档里的目标架构相比，当前代码已经升级到“基座驱动”，但仍保留主应用适配层

这不是坏事，是渐进式迁移的现实状态。讲解时要区分“目标设计”和“当前实现”。
能力 目标设计 当前代码落地 你讲解时的措辞
Bootstrap 由基座内置通用启动流程 `BootstrapApp.run()` 已在 micro-base 中收敛 “主应用把配置交给基座执行”
Module 子应用可独立注册路由/状态/组件 已有 load/register API；主应用仍显式 import 部分子应用模块 “正在从主应用拼装走向子应用自注册”
Global Data 统一收敛共享属性 基座有 setGlobalData；业务 API 仍有 `window.__GLOBAL_DATA__` “核心实例收敛，业务共享数据仍在过渡”
React migrate 磨平技术栈差异 convertReactRoutesToVue / loadComponent 已落地 “Vue 宿主可以承载 React 页面”

14 / 难点

难点不在“能不能加载”，而在版本、边界、容错、权限和初始化顺序

这些是讲解时最该主动点出来的风险点，也是日常排障里最常见的坑。
1
shared 版本冲突React、Vue、router、store、UI 组件被 singleton 共享，版本不齐容易产生 hook、路由或样式问题。
2
publicPath / chunk 404remoteEntry 加载成功不代表页面成功，后续 chunk 可能因为路径不对请求错域名。
3
路由 name 与权限菜单依赖 registeredRoutes，name 重复、meta.hidden、permissions 都会让菜单看起来“消失”。
4
初始化时机依赖 `$gt`、i18n、global data 的模块如果过早静态 import，会出现 undefined 或语言包异常。
5
业务共享数据边界request/API/Utils 仍有主应用注入，子应用需要知道哪些来自基座，哪些来自当前 Portal。
6
错误隔离远程模块加载失败可能影响主流程，需要 fallback、日志和可定位的错误信息。

15 / 排障路线

排障时按“入口 - 远端 - 模块 - 注册 - 权限 - 渲染”走，不要一上来改业务页面

这张可以作为你讲解后的实战页，也可以直接发给同学做自查。
1. 页面白屏或启动失败看 console 第一条错误；如果是 shared/eager/module not found，先看 remoteEntry 与 shared 版本。
2. remoteEntry 404检查 `remotes.ts` 的 module name、entry path、env/local 配置和 Network 请求地址。
3. chunk 404检查子应用 `publicPath`，本地 devServer 要允许跨域并返回绝对路径资源。
4. 模块导出 undefined确认 exposes key 和 import key 一致，例如 `scsProductPms/routes` 是否真的导出 `productModule`。
5. 路由能进但菜单不显示看 `registeredRoutes`，再看 `meta.hidden`、`permissions`、父路由 `Root`、`isMultipleMenu` 子节点。
6. React 页面空白看 ReactContainer/ReactWrapper 错误，确认 component 是 lazy 函数还是 Promise import。
7. 请求或语言异常确认 init-global-data、i18n 初始化是否在业务模块 import 前完成。
8. 只在本地异常先排查本地 remote 覆盖、端口、CORS、cookie/domain，再看业务逻辑。

16 / 讲解主线

你可以按这条线讲：从协作问题出发，到运行时拼装，再落到排障方法

这页是你的演讲提纲。每一段都能回到代码或文档，不需要背抽象概念。
为什么拆
多团队发布耦合，主应用侵入成本高，需要业务代码自治。
谁负责什么
主应用负责壳，基座负责运行时，子应用负责业务模块。
怎么启动
BootstrapApp 创建实例，插件在生命周期里注册模块。
怎么拼装
remoteEntry 加载模块，routes/store/components 注册进同一运行时。
怎么排障
入口、远端、模块、注册、权限、渲染六步定位。
收尾话术：这套架构的价值，是让不同团队的业务模块可以独立演进，同时让用户仍然看到一个统一的 Retail Portal。
