**一页总结**

`asset-ui` 是主应用，也是基座；`asset-mfe` 是子应用仓库。  
它们不是简单的“主应用加载一个远端页面”，而是：

- `asset-ui` 暴露自己的启动能力 `Shared/app`
- `asset-mfe` 暴露自己的业务模块 `AssetPC/module`
- 主应用负责统一注册路由、菜单、store 和上下文
- 子应用负责输出业务页面、业务路由、业务模块定义
- Vue 壳子里通过桥接容器承载 React 页面

你可以把它理解成：

> `asset-ui` 是装配工厂，`asset-mfe` 是业务零件仓库，Module Federation 是运输和装配协议。

**10 分钟讲稿**

1. 先讲角色分工

“这套架构里有两个核心仓库。`asset-ui` 是主应用，它不只是页面入口，更像一个基座，负责启动流程、Vue Router、Vuex、菜单、权限、翻译和公共上下文。`asset-mfe` 是子应用仓库，主要承载按业务域拆分出来的 React 模块，比如 `asset-pc`。”

“所以这里不是 iframe，也不是一个完整站点套另一个完整站点，而是主应用在运行时把子应用当成业务模块装配进来。”

2. 再讲 Module Federation 的双向关系

“这里有个很有意思的点，`asset-ui` 和 `asset-mfe` 是双向依赖的。”

在 [webpack.config.js](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/webpack.config.js:226) 里：

```js
new ModuleFederationPlugin({
  name: 'Shared',
  filename: 'sharedEntry.js',
  exposes: {
    './app': path.resolve(__dirname, 'src/app/main.js'),
  },
  remotes: {
    AssetPC: 'promise window.LOAD_REMOTE_ENTRY("AssetPC", "asset-pc", "remoteEntry.react.js")',
  },
})
```

你可以这样讲：

“`asset-ui` 一方面暴露了 `Shared/app`，也就是它自己的启动能力；另一方面它又声明自己要消费远端的 `AssetPC` 子应用。”

而在子应用 [moduleFederationConfig.js](/Users/zhuangbing.cai/Desktop/资料/asset/asset-mfe/apps/asset-pc/config/moduleFederationConfig.js:17) 里：

```js
module.exports = {
  name: moduleName,
  filename: 'remoteEntry.react.js',
  exposes: {
    './module': paths.mfModule,
  },
  remotes: {
    Shared: 'promise window.LOAD_REMOTE_ENTRY("Shared", "ssc-assets", "sharedEntry.js")',
  },
  shared: dependenciesShared,

```

你可以这样解释：

“子应用反过来也依赖主应用暴露的 `Shared/app`。所以它不是独立启动一个完整 React App，而是借助主应用提供的运行时壳子，把自己的模块挂进去。”

3. 讲运行时加载链路

“真正的运行链路分四步。”

第一步，主应用知道去哪里找 remote entry。  
在 [moduleEntryBaseURL.ts](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/src/moduleEntryBaseURL.ts:45) 里，定义了 `window.LOAD_REMOTE_ENTRY`。它会根据 `appId` 拼出资源地址，然后动态插入 script 去加载 `remoteEntry.react.js`。

第二步，主应用在启动时 import 子应用模块。  
在 [init.ts](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/src/init.ts:23) 里：

```ts
const importMap = {
  assetpcstatic: () => [
    {
      initModule: import('AssetPC/module'),
    },
  ],
};
```

你可以讲成：

“主应用并不是写死一个页面组件，而是在启动阶段动态 import `AssetPC/module`，拿到子应用导出的模块描述。”

第三步，主应用的 `run()` 负责装配。  
在 [main.js](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/src/app/main.js:37)：

```js
export async function run(modules) {
  const preTaskList = [prepareModuleSource(modules), initTransilation(...)]
  await Promise.all(preTaskList)
  ...
  new Vue({ router, store, i18n, render: (h) => h(App) })
}
```

你可以讲：

“这里真正做了两件事：先把所有子应用模块注册进来，再启动 Vue 根实例。”

第四步，子应用模块被注册成路由、菜单和 store。  
在 [module-federation.ts](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/src/app/register/module-federation.ts:80) 里，`registerModule()` 会读取子应用导出的 `routes`、`stores`、`menus`、`packageInfo`，然后：

- `router.addRoute(route)`
- `store.registerModule(...)`
- `store.commit('addMenus', menus)`

你可以用一句话收住：

“所以子应用导出的不是一个‘完整网站’，而是一份业务模块说明书，主应用读这份说明书完成装配。”

4. 讲 React 和 Vue 怎么混跑

“这套架构虽然主壳子是 Vue2，但子应用很多页面是 React。它能跑起来，不是因为 Vue 直接理解 React，而是中间有一层桥接。”

在 [react-project.tsx](/Users/zhuangbing.cai/Desktop/资料/asset/asset-mfe/apps/asset-pc/src/moduleEntries/react-project.tsx:3) 里，子应用导出：

```ts
export default {
  isReact: true,
  routes: vueRoutes,
  reactRoutes,
}
```

也就是说，子应用会同时提供：

- `reactRoutes`
- 转换后的 `vueRoutes`

而主应用侧的桥接在 [bridge.ts](/Users/zhuangbing.cai/Desktop/资料/asset/asset-ui/src/utils/bridge.ts:30)：

```ts
const vueRoutes = reactRoutes.map(item => {
  ...
  finalComponent = reactContainerFactory({ name: item.name });
})
```

你可以这样讲：

“Vue Router 最终只认识 Vue route，所以 React route 会先被包装成一个 Vue 容器组件，真正渲染的时候再由这个容器去挂 React 页面。这样宿主仍然是 Vue，但业务页面可以是 React。”

5. 最后讲这套设计的价值

“这套架构的价值主要有三点。”

- 主应用和子应用职责更清晰  
  主应用管壳子和上下文，子应用管业务模块
- React 业务可以渐进接入 Vue 老系统  
  不需要一次性重写整站
- 业务域可以拆仓开发  
  `asset-mfe` 可以专注 React 业务模块演进

**你可以直接背的收尾总结**

“总结一下，`asset-ui` 在这套架构里既是 host，也是 base；`asset-mfe` 提供的是业务模块而不是完整独立站点；Module Federation 负责模块发现和加载；主应用统一注册路由、菜单和 store；React 页面通过桥接容器挂进 Vue 壳子。整个系统的核心不是页面跳转，而是运行时模块装配。”

**最容易被问到的 5 个问题**

1. 为什么主应用也要 `exposes`？
因为它不仅消费子应用，也要把自己的启动能力 `Shared/app` 暴露给子应用使用。

2. 为什么子应用不自己 `ReactDOM.render`？
因为它不是独立站点，它要接入主应用已有的 router、store、权限、翻译和布局体系。

3. 为什么要同时有 `reactRoutes` 和 `vueRoutes`？
因为业务页面本质是 React 写的，但最终挂载体系是 Vue Router，所以需要桥接。

4. 这是不是 iframe？
不是。它是运行时模块装配，页面最终仍然在同一个前端应用上下文里。

5. 最容易出什么问题？
远端 entry 路径错误、shared 依赖版本不一致、路由 basename 不一致、store 重名、React/Vue 桥接容器渲染异常。
