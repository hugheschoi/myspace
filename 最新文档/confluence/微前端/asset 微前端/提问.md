**高频追问**

1. 为什么 `asset-ui` 也要 `exposes`，它不是主应用吗？  
可以答：

“因为这里的主应用不只是 host，它还承担了 base 的职责。`asset-ui` 暴露 `Shared/app`，本质上是在把自己的启动能力、上下文和装配入口开放出来。子应用不是独立跑一个 React 站点，而是借这个入口接入主应用的 router、store、权限和翻译体系。”

2. 为什么子应用还要反向依赖主应用？  
可以答：

“因为这套方案不是完全自治的微前端，更像模块化装配。子应用负责输出业务模块，但运行时壳子和公共上下文都在主应用，所以它反向消费 `Shared/app` 是为了复用主应用的启动和注册流程。”

3. 为什么不直接让主应用 `import('AssetPC/module')` 然后自己渲染？  
可以答：

“其实已经在 import 了，但 import 到的不是一个普通页面组件，而是一份模块描述。里面有 routes、stores、menus、packageInfo 这些信息。主应用拿到之后统一注册，这样才能保持菜单、路由、权限、布局、store 都在同一个体系里。”

4. 为什么 React 页面能跑在 Vue 壳子里？  
可以答：

“因为中间做了桥接。React route 不会直接塞给 Vue Router，而是先转换成 Vue 可识别的 route，再用一个 React 容器组件承载真实 React 页面。Vue 负责导航和布局，React 负责具体业务页面渲染。”

5. 这和 iframe 最大区别是什么？  
可以答：

“iframe 是页面级隔离，这套是模块级装配。iframe 的路由、store、权限、上下文都是分裂的；这里主子应用共享同一个运行时体系，体验更一致，集成更深，但装配复杂度也更高。”

**容易被深入追问的点**

1. 主应用启动时到底先做什么？  
答法：

“先准备远端模块，再注册模块，再启动 Vue 根实例。`asset-ui` 的 `run()` 里会先执行 `prepareModuleSource(modules)`，把子应用 routes、stores、menus 注册进去，然后再 mount 主应用。”

2. 子应用暴露的 `./module` 里面到底是什么？  
答法：

“不是一个单页组件，而是一个模块对象。以 `asset-pc` 为例，它会导出 `isReact`、`routes`、`reactRoutes`、`packageInfo` 等信息。主应用根据这些信息决定怎么装配。”

3. 为什么子应用还要导出 `vueRoutes`，不是 React 项目吗？  
答法：

“因为宿主的导航体系还是 Vue Router。React 页面本体不变，但为了挂进 Vue 的路由树，需要先生成一份 Vue 可消费的 route 结构。”

4. `shared` 的意义是什么？  
答法：

“是为了让主应用和子应用尽量共用一份依赖实例，尤其是 React、ReactDOM、UI 组件库这类运行时依赖。否则可能出现重复实例、上下文断裂、hook 异常或者样式体系不一致的问题。”

**你可以主动补的一句**

别人如果问得很技术，你可以主动加一句：

“这套架构的关键其实不是 `ModuleFederationPlugin` 这几行配置本身，而是运行时约定：remote 怎么找、模块导出什么、主应用怎么注册、React 怎么桥接进 Vue、公共依赖怎么共享。这几个约定一旦清晰，整套系统就很好理解了。”

**一句最稳的总括**

“`asset-ui` 提供壳子和装配能力，`asset-mfe` 提供业务模块，Module Federation 负责把两边在运行时接起来；最终页面虽然有 Vue 和 React 两种技术栈，但对用户来说仍然是一套统一的资产系统。”
