01

Core Judgment

生码 Harness 的关键，不是换更强模型，而是给生成过程加工程约束

模型能力很强，但如果缺少任务边界、项目上下文、工具管控、校验和反馈，结果会快但容易跑偏。

从 0 到 1 的正确姿势：先跑通一个最小闭环，再按真实失败逐层增加约束。

Direction

知道去哪里

任务契约、输入规范、验收标准。

Context

看清路况

PRD、TD、接口、模板、代码上下文。

Control

安全路线

文件边界、权限、沙盒、工具网关。

Feedback

每步反馈

lint、typecheck、测试、截图、CR。

Memory

失败沉淀

归因、规则、模板、评测回流。

02

Goal

目标不是“让 AI 写代码”，而是让 AI 在工程体系里交付代码

输出形态要从文本片段升级为可验收、可复盘、可接入研发流程的任务交付包。

NO不止是代码片段

  • 需求靠猜，接口靠补
  • 结果看似完整，落地成本高
  • 失败原因没有进入下一轮
  • 交付质量依赖使用者经验

OK工程 Diff + 验证报告

  • 代码改动、接口类型、页面实现
  • 变更说明、验证结果、风险提示
  • 未完成项、复盘日志、规则沉淀
  • 能被 CI、CR 和人工验收接住
D工程 Diff
T类型与接口
V验证结果
R风险与复盘

Minimum Loop

第一版 Harness 先跑通一条最小闭环

闭环跑通后，系统才从“裸奔生成”进入“可控交付”。

01

任务输入

把一句需求规整成 Task Spec。

02

上下文收集

读取代码、接口、组件和规范。

03

生成计划

形成文件、接口、验证计划。

04

执行改码

在受控范围内编辑代码。

05

自动验证

lint、typecheck、test、build。

06

失败修复

把错误注入上下文再修复。

07

输出总结

记录结果、风险和未完成项。

04

Core Modules

Harness 的七个核心模块

第一版不需要很复杂，只要每个环节职责清楚，链路就能逐渐产品化。

SPEC

Task Spec

定义任务边界、输入来源和验收标准。

CONTEXT

Context Collector

收集代码、接口、组件、历史页面和规范。

PLAN

Planner

生成文件改动、接口接入和组件拆分计划。

EXECUTE

Executor

创建页面、补类型、接接口、写状态逻辑。

VERIFY

Verifier

执行 lint、typecheck、test、build、截图。

FEEDBACK

Feedback Loop

把失败日志转为下一轮修复上下文。

REPORT

Reporter

说明改了什么、如何验证、风险是什么。

05

Layer 1

第一层约束：任务输入契约

输入太散时，Agent 会猜需求、猜接口、猜组件、猜状态，稳定性自然下降。

task:
  name: 新增订单列表页
  type: page
  target_route: /order/list

sources:
  prd: xxx
  yapi:
    - /api/order/list

constraints:
  component_library: SSC UI React
  editable_scope:
    - src/pages/order

acceptance:
  - 支持筛选、分页、导出
  - typecheck 通过
  - lint 通过
1

任务边界

明确做什么、不做什么、目标路由和可编辑范围。

2

输入来源

把 PRD、TD、YAPI、模板和相似页面纳入契约。

3

验收标准

把功能、类型、lint、测试和禁区都写清楚。

06

Layer 2

第二层约束：上下文工程

不是一次塞满所有资料，而是按任务类型稳定注入“必须上下文”。

需求上下文

PRD、TD、验收标准，回答要做什么。

接口上下文

YAPI、字段类型、请求方法，回答数据从哪里来。

代码上下文

目录结构、相似页面、工具函数，回答项目怎么组织。

组件上下文

组件库文档、示例、API，回答 UI 怎么拼。

规范上下文

权限、埋点、i18n、代码规范，回答边界和习惯。

必须注入什么
相关文件怎么检索
相似页面取几份
长文档怎么摘要
接口如何转类型
规则放在哪一层
哪些信息按需查询
如何避免上下文噪声

Layer 4

第四层约束：执行沙盒

沙盒不是让 Agent 变弱，而是让它可以放心地变强。

安全边界先于自动化规模

写文件、跑命令、装依赖、调用接口都需要边界；边界稳定后，自动化才敢深入工程核心。

每个任务使用独立分支或 worktree
限制可编辑目录和公共基础设施改动
新增依赖、高风险命令需要人工确认
命令执行有超时和结果记录
成熟后加入容器、网络白名单和资源配额

10

Layer 6

第六层约束：失败处理与重规划

系统成熟度不在于是否失败，而在于失败后能否分类、修复和停止。

类型错误注入错误日志，自动修复。
接口字段回查 YAPI，重新生成类型。
组件 API查询组件文档，替换用法。
测试失败定位断言，修复业务逻辑。
构建失败判断依赖、路径和导出问题。
需求不明暂停并向人提问。
越权修改回滚该部分改动并上报。
可确定问题：自动修 1-3 轮
不确定问题：停止并输出问题
高风险问题：请求人工确认

Layer 7

第七层约束：记忆与经验沉淀

真正的驯化，是让 Agent 下次少犯同类错误。

每次失败后都问：这个问题应该沉淀成什么？

Harness 的核心理念，是不要让模型在同一个坑里反复摔。

Roadmap

从 0 到 1 的迭代路线

不要一开始造大平台；从人工辅助到最小闭环，再走向平台化和规模化。

P0 人工辅助型

让 Agent 按规范生成代码，但主要由人提供上下文。

  • 任务模板
  • 固定 Prompt
  • 人工贴 PRD/TD/YAPI
  • Agent 改码
  • 人工跑验证

P1 最小闭环

让 Agent 自动收集基本上下文，并能自动验证。

  • Task Spec
  • 相似页面和组件文档
  • 读取 YAPI
  • 自动跑 lint/typecheck
  • 失败后修复 1-2 轮

P2 可控平台

让生码过程具备权限、边界、审计和可恢复能力。

  • 工具网关
  • 文件范围控制
  • 命令白名单
  • 检查点
  • CR Shift-Left

P3 规模化 Harness

让系统能持续学习，并在更多任务类型里复制。

  • 任务类型分类
  • 多模板体系
  • 评测集
  • 历史失败记忆
  • CI/CD 集成

16

Principle

一句话落地原则

从 0 到 1 做 Harness，先在窄场景里做到稳定闭环。

输入清楚、上下文充分、工具受控、执行安全、验证自动、失败可修、经验可沉淀。

这时它才不再只是生码能力，而是开始具备工程交付能力的可驯化生产力。
