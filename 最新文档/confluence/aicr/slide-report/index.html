IBS CLI Deep Dive

项目结构与关键代码深度梳理

围绕 @shopee/ibs-cli 的 CLI 入口、CR Shift-Left 主链路、Git diff 采集、Cursor 深链、Git hooks 管理与工程风险进行完整拆解。

Node.js CommonJS Commander CLI Git Hooks Cursor Deep Link CR Session API
一句话定位
本地 CLI 负责采集 Git 仓库上下文与 diff。
服务端负责创建代码审查 session、分批和去重。
Cursor 负责执行最终的 AI code review 工具调用。
Git hooks 负责把审查动作前置到 push 流程。
01 / 全局结论

这不是一个“自己做 AI Review”的 CLI

它更像本地上下文采集器、审查 session 启动器、Cursor prompt 触发器和 Git hook 分发器的组合。

ibs
全局命令名，由 package.json 的 bin 字段暴露。
cr
核心命令，采集 diff 后创建 CR session。
hooks
可全局安装，也可本地注入 pre-push 包装脚本。
Cursor
通过 deep link 打开 prompt，而不是在 CLI 内完成审查。
核心设计取舍：把“Git 本地上下文”留在开发机，把“审查任务管理”放到后端，把“AI 执行入口”交给 Cursor。

02 / 包信息

包身份、运行环境与依赖

项目是一个极轻依赖的 Node.js CLI，当前版本 1.2.4，运行时只依赖 commander 和 chalk。

{
  "name": "@shopee/ibs-cli",
  "version": "1.2.4",
  "type": "commonjs",
  "bin": { "ibs": "bin/index.js" },
  "dependencies": {
    "chalk": "^4.1.2",
    "commander": "^11.0.0"
  },
  "engines": { "node": ">=16.0.0" }
}

工程含义

  • CommonJS 模块体系，所有 lib 通过 require 组装。
  • 命令行框架使用 commander，命令注册集中在 bin/index.js。
  • HTTP 没有引入 axios/fetch 封装，而是通过 curl 子进程完成。
  • 跨平台能力主要依赖系统命令：open、osascript、xdg-open、PowerShell。

PART A

CLI 入口与命令设计

先从用户输入如何变成具体模块调用开始看。这个项目的组织方式很直接，入口文件承担了依赖装配和命令分发。

05 / CLI 装配

CursorCLI 构造函数就是依赖注入中心

所有工具类在构造函数里实例化，随后 setupCommands 将命令与方法绑定。

class CursorCLI {
  constructor() {
    this.program = new Command();
    this.platformUtils = new PlatformUtils();
    this.systemUtils = new SystemUtils();
    this.clipboardManager = new ClipboardManager(this.platformUtils);
    this.cursorInteraction = new CursorInteraction(this.platformUtils);
    this.gitUtils = new GitUtils();
    this.userInteraction = new UserInteraction();
    this.configManager = new ConfigManager();
    this.codeReview = new CodeReview(
      this.platformUtils,
      this.gitUtils,
      this.userInteraction
    );
    this.gitHooksManager = new GitHooksManager();
    this.setupCommands();
  }
}

设计特点

  • 依赖显式传入，CodeReview 不自己 new GitUtils，便于替换。
  • 大多数模块无状态，状态主要来自当前工作目录、环境变量和 Git 仓库。
  • 入口文件里保留了不少已注释命令，说明项目从 Cursor 通用助手逐步收敛到 CR 场景。

PART B

CR Shift-Left 主链路

这是项目最核心的业务流程：本地决定审查范围，后端创建任务，Cursor 发起工具调用。

07 / 端到端流程

从 ibs cr 到 Cursor 工具调用

CLI 不直接产出审查结果，而是将 session_id 交给 Cursor 环境里的 cr_shift_left_batch_review。

1

用户触发

手动执行 ibs cr，或 pre-push hook 自动执行。

2

识别模式

rerun、MR URL、staged、branch/commit 四类路径。

3

采集上下文

workspace、user、project_id、rules、diff、commits。

4

创建 session

POST 到 /api/quality/cr/session/setup。

5

唤起 Cursor

deep link 写入 prompt，要求调用 batch review 工具。

must call cr_shift_left_batch_review({
  session_id: "..."
})

Always reply in Chinese.

08 / 审查模式

四种入口路径决定 diff 来源

模式选择发生在 CodeReview.runCodeReview() 早期，优先级会影响用户感知。

rerun

已有 session 复跑

  • 参数：--rerun=session_id=xxx
  • 不重新收集 diff，不访问 Git。
  • 直接生成 Cursor prompt。
MR URL

服务端从 GitLab 获取 diff

  • 第一个参数匹配 /-/merge_requests/\d+。
  • 本地只上传 MR URL、workspace、user、rules。
staged

暂存区优先

  • 只要 git diff --cached 有内容就启用。
  • 适合提交前审查已 staged 代码。
branch

分支或 commit 对比

  • 无 staged changes 时启用。
  • 可交互输入，也可传 base head。
  • 会 fetch 远程基准分支。

09 / Session Payload

上传给后端的字段是 GitLab MR 语义

本地参数名有历史包袱，但最终 payload 用 source_branch 表示新代码分支，target_branch 表示基准分支。

{
  workspace,
  user_name,
  files,
  commits,
  project_id,
  jira_id,
  source_branch,
  target_branch,
  current_branch,
  commit_id_base,
  commit_id_head,
  diff_type,
  cursor_rules,
  extra_params,
  auto_fixed,
  version
}
workspace
当前执行目录，通常是 Git 仓库根目录或子目录。
files
过滤后的变更文件，每项包含路径、变更行数和 diff 内容。
cursor_rules
从 .cursor/rules 中扫描并压缩后的规则数据。
auto_fixed
--no-fix 通过 commander 反转为 options.fix === false。

10 / HTTP 实现

HTTP 层用 curl 子进程，而非 JS HTTP 客户端

请求体先写入临时 JSON 文件，再通过 --data-binary @file 上传，最后一行用 --write-out 取 HTTP 状态码。

const tmpFile = path.join(os.tmpdir(),
  `cr-request-${Date.now()}.json`
);
fs.writeFileSync(tmpFile, JSON.stringify(data));

const curlCmd = `curl -X POST "${url}" \
  -H "Content-Type: application/json" \
  --data-binary @"${tmpFile}" \
  --max-time ${timeout} \
  --silent \
  --show-error \
  --write-out "\n%{http_code}"`;

为什么这样写

  • 避免大 payload 在 shell 字符串中转义困难。
  • 不用引入额外 HTTP 依赖。
  • maxBuffer 设置到 50MB，用于容纳较大响应。
风险：依赖系统 curl；URL 和命令字符串仍经过 shell，长期看应迁移到 Node 原生 fetch 或 undici。

PART C

Git 数据采集与 diff 解析

这是本地 CLI 最有价值的部分：尽量准确、轻量地把本地变更变成服务端可处理的数据结构。

13
11 / Diff 采集

一次 git diff 同时拿统计和补丁

命令使用 --numstat --patch，先解析文件行数，再解析每个文件的 patch 内容。

branch 模式

git diff \
  origin/base...head \
  --diff-filter=d \
  --numstat \
  --patch
  • 分支对比使用三点语法。
  • commit 对比时改用空格语法。
  • 删除文件通过小写 d 排除。

staged 模式

git diff \
  --cached \
  --diff-filter=d \
  --numstat \
  --patch
  • 只审查已暂存内容。
  • 新增、修改、重命名会保留。
  • 测试、mock、docs 等再由过滤规则排除。
14
12 / Parser 细节

解析分两段：numstat 建索引，patch 填内容

文件是否进入最终列表，由扩展名 include 和路径 exclude 双重控制。

const fileStats = new Map();

// 1. numstat: added deleted file
if (filterRegex.test(file) && !excludeRegex.test(file)) {
  fileStats.set(file, {
    diff_lines: addedNum + deletedNum
  });
}

// 2. patch: diff --git a/x b/x
if (currentFile && fileStats.has(currentFile)) {
  fileDiffs.push({
    file_path: currentFile,
    diff_lines: fileStats.get(currentFile).diff_lines,
    diff: this.compressContent(currentDiff.trim())
  });
}

关键点

  • numstat 提供行数，patch 提供上下文。
  • diff 内容用 gzip 后 base64，便于 JSON 传输。
  • maxBuffer 放大到 200MB，以适配较大 diff。
  • 最后一个文件当前没有压缩，是需要重点修的实现不一致。

13 / 文件过滤

过滤配置优先远程，失败时默认兜底

FilterConfigCache 不是传统缓存，每次都会尝试请求远程配置；失败再回退到硬编码规则。

远程配置

  • GET /api/quality/cr/config
  • 读取 data.fileFilter
  • 支持字符串或数组格式

默认 include

  • ts / js
  • vue / tsx / jsx
  • go

默认 exclude

  • mock / __mocks__
  • config / d.ts
  • test / spec / unit
  • docs / demo / README
过滤放在本地执行，能减少上传体积和后端解析压力；远程配置让规则可以集中调整。

14 / Cursor Rules

项目自定义审查规则会被扫描并压缩

扫描路径是 .cursor/rules/**/code-review/cr-*.mdc，这让不同项目可以提供自己的审查标准。

const rulesBaseDir = path.join(
  projectRoot,
  '.cursor/rules'
);

if (/code-review[\/\\]cr-.+\.mdc$/
  .test(relativePath)) {
  files.push({
    path: path.relative(projectRoot, fullPath),
    content,
    size
  });
}

返回结构

  • compressed_data：完整规则 JSON gzip+base64。
  • original_size / compressed_size：用于日志展示压缩率。
  • files：只保留路径和大小，用于 CLI 输出。
这部分是项目差异化能力的入口：同一个 CLI 可以服务不同仓库的规则体系。

PART D

Cursor 与协议联动

从当前代码看，CR 主链路已经从“剪贴板 + 快捷键模拟”转向更稳定的 Cursor deep link。

15 / Cursor 发送

当前 CR 使用 cursor:// 深链发送 prompt

这条路径不需要先聚焦 Cursor、清空输入框、粘贴、回车，减少了对辅助功能权限的依赖。

async sendMessageToCursor(message) {
  await this.clipboardManager.openCursorPrompt(message);
}

async openCursorPrompt(text) {
  const encoded = encodeURIComponent(text);
  const url =
    `cursor://anysphere.cursor-deeplink/prompt?text=${encoded}`;
  exec(platformCommand(url));
}

两代方案对比

方案特点
旧路径打开 Cursor、快捷键、剪贴板、粘贴、回车；对系统权限敏感。
新路径通过 URL Scheme 直接把 prompt 交给 Cursor；更短、更稳。

16 / ibs:// 协议

浏览器触发 CLI 的 macOS URL Scheme

ibs-protocal.js 会编译 AppleScript App，并注册成 ibs:// 的默认处理程序。

注册位置
~/Library/Application Support/IBSProtocol.app，指纹保存到 ~/.ibs-cli/protocol-fingerprint.json。
触发格式
ibs://cr?workspace=/path&session_id=xxx，其中 workspace 会被提取成工作目录。
执行方式
AppleScript 写入 /tmp/ibs-cr.command，再用 Terminal 打开执行。
rerun 转换
除 workspace 外的 query 参数会重新组合成 ibs cr --rerun=...。
日志位置
/tmp/ibs-proxy.log，用于排查 URL Scheme 是否触发。

PART E

Git Hooks 管理机制

hooks 是这个 CLI 最容易影响用户环境的部分：既要自动触发 CR，又要尽量不破坏已有 hook 体系。

21
17 / 全局 Hooks

全局模式通过 core.hooksPath 接管 Git hooks

安装时创建 ~/.git-hooks，写入 hook 文件，然后设置 Git 全局 hooksPath。

支持类型

  • pre-push
  • pre-commit
  • post-commit

安装动作

  • 校验 hook 类型。
  • 备份非 IBS 旧 hook。
  • 写入 755 权限脚本。

Git 配置

  • git config --global core.hooksPath
  • 已有路径会被提示并覆盖。
  • 卸载空目录时 unset。
全局 hooksPath 是强影响配置：它会改变所有仓库的 hook 查找路径，需谨慎告知用户。
22
18 / pre-push 脚本

push 前计算 base/head，并运行 ibs cr

这个 hook 是辅助型：AI CR 异常不会阻止 push，但本地原 hook 或 Husky hook 失败会阻止。

1

读取 stdin

Git 传入 local ref/sha、remote ref/sha；stdin 只能读取一次，所以会缓存。

2

处理新分支

remote sha 为零时，尝试用 origin 默认分支求 merge-base。

3

设置环境

导出 IBS_BASE_SHA 和 IBS_HEAD_SHA。

4

运行 CR

执行 ibs cr BASE HEAD；可用 IBS_NO_CR=1 跳过。

5

转发本地 hook

调用 .git/hooks 或 .husky 中原有 hook。

README/注释中出现 git push --no-cr，但 Git 原生命令不接受这个自定义参数；当前可靠方式是环境变量。
23
19 / 本地注入

本地注入的重点是“包装而不是覆盖”

它会根据仓库现有 hooks 配置选择不同策略，尽量保存原 hook 并在 IBS 之后继续执行。

检测结果判断方式注入策略
husky存在 .husky 或 hooksPath 指向 .husky直接包装 .husky/pre-push
local custom仓库级 core.hooksPath在自定义路径中包装 pre-push
global全局 core.hooksPath创建本地 .git/hooks 覆盖，并给其他全局 hook 建软链
default没有 hooksPath包装默认 .git/hooks/pre-push
备份文件统一命名为 pre-push.ibs-backup，卸载时优先恢复备份。

20 / lifecycle 脚本

postinstall/preuninstall 写了，但当前 package.json 未注册

scripts 目录表达了本地安装自动注入 hook、卸载恢复 hook 的意图，但当前包定义里没有 lifecycle scripts 字段。

postinstall.js 的意图

  • 判断全局安装还是本地安装。
  • 本地安装时定位项目根目录。
  • 调用 manager.injectLocalHook('pre-push')。
  • 调试日志写入 /tmp/ibs-cli-postinstall.log。

当前快照的问题

  • package.json 中没有 scripts.postinstall。
  • package.json 中没有 scripts.preuninstall。
  • 因此 npm 安装时不会自动执行这些文件。
  • 除非发布流程另有注入，否则这部分只是未接线能力。
如果希望本地安装自动生效，应显式在 package.json 增加 lifecycle scripts，并补充安全提示与测试。

PART F

风险点与改进路线

这部分把代码阅读转化为工程判断：哪些点会出问题，哪些点最值得先修。

21 / 关键风险

最需要关注的 6 个问题

这些点来自当前代码实现，而不是泛泛而谈的 CLI 风险。

Bug

最后一个 diff 未压缩

前面文件用 gzip+base64，最后一个文件直接存原文，可能导致后端解码不一致。

Shell

命令拼接注入风险

分支名、路径、URL 多处进入 shell 字符串，遇到特殊字符可能失败或更严重。

Git

全局 hooksPath 覆盖

安装全局 hooks 会影响所有仓库，用户已有全局 hook 管理体系可能被替换。

Docs

--no-cr 文档不准确

Git 不接受 git push --no-cr，实际应使用 IBS_NO_CR=1 git push。

Lifecycle

脚本未接线

postinstall/preuninstall 存在但 package.json 未注册，安装时不会自动触发。

Test

缺少自动化测试

当前没有测试脚本；diff parser、hook wrapper、URL scheme 都缺验证。

22 / 改进路线

优先级建议：先正确，再安全，最后体验

如果后续要继续维护，我建议按风险闭环来排期，而不是先堆新命令。

优先级建议原因涉及文件
P0修复最后一个 diff 未压缩直接影响服务端数据一致性。lib/git-utils.js
P0为 diff parser 加单测覆盖新增、修改、重命名、删除、过滤、最后文件。test/
P1替换 shell 拼接为 spawn args 或原生 API降低特殊字符和注入风险。git-utils.js、code-review.js
P1明确 hooks 安装策略全局 hooksPath 影响面很大，需要用户确认或文档强化。git-hooks-manager.js
P2整理 README 和命令帮助删除过时的 --no-cr 表述，补齐 MR/rerun/deep link。README.md
P2决定 lifecycle 是否启用启用则补 package scripts；不用则删除或标注手动入口。package.json、scripts/

24 / 收束

把这个项目理解成“三段式管道”最清楚
