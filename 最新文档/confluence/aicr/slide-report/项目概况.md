**项目全貌**
这是一个内部 Node.js CLI 项目，包名是 `@shopee/ibs-cli`，全局命令叫 `ibs`，定位是“本地代码审查启动器”：它从当前 Git 仓库采集 diff、commit、分支、项目、规则文件等上下文，上传到后端创建 CR session，然后把一条调用 `cr_shift_left_batch_review` 的 prompt 发送给 Cursor。入口和包信息在 [package.json](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/package.json:2) 和 [bin/index.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/bin/index.js:22)。

**一句话架构**
`ibs-cli = Commander 命令入口 + Git 上下文采集 + 后端 CR session 创建 + Cursor 深链唤起 + Git hooks 自动触发层`。

当前真正注册的命令主要有三类：

1. `ibs cr`：启动代码审查，支持暂存区、分支对比、commit 对比、MR URL、rerun。
2. `ibs update` / `ibs upgrade`：从 Shopee npm registry 升级 CLI。
3. `ibs hooks`：安装、卸载、注入、移除、查看 Git hooks。

有一些旧能力还留在代码里，比如 `send/chat/watch/status/config/permissions`，但注册命令被注释掉了，所以当前用户不能直接通过 CLI 调用这些命令，见 [bin/index.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/bin/index.js:48)。

**核心运作流程**
执行 `ibs cr` 后，入口在 [bin/index.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/bin/index.js:162)。它会调用 `CodeReview.runCodeReview()`。

正常流程是：

1. 识别是否是 rerun。`--rerun=session_id=xxx` 会跳过 Git diff 收集，直接生成 Cursor prompt。
2. 识别是否是 MR URL。形如 `https://.../-/merge_requests/123` 会进入 MR 模式，diff 由服务端从 GitLab 获取。
3. 获取本地上下文：当前目录、用户名、Git remote 推导出的 `project_id`、`.cursor/rules/**/code-review/cr-*.mdc` 自定义规则。
4. 判断是否有 staged changes。
5. 有暂存区变更时走 staged 模式，审查 `git diff --cached`。
6. 无暂存区变更时走 branch 模式，比较基准分支和审查分支。
7. 收集文件 diff、commit list、JIRA ID、commit hash。
8. POST 到后端 `/api/quality/cr/session/setup` 创建 session。
9. 后端返回 `session_id` 后，生成 Cursor prompt：`must call cr_shift_left_batch_review({ session_id })`。
10. 通过 Cursor 深链发送到 Cursor，见 [bin/index.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/bin/index.js:361) 和 [clipboard-manager.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/clipboard-manager.js:120)。

**CR 的三种模式**
`staged` 模式：只要暂存区有内容，就优先审查暂存区。它把 `commit_id_base` 和 `commit_id_head` 都设为 `HEAD`，diff 来自 `git diff --cached --diff-filter=d --numstat --patch`，见 [code-review.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/code-review.js:210)。

`branch` 模式：没有暂存区变更时启用。用户可以传 `ibs cr release feature/x`，也可以交互输入。它会验证 ref、必要时切到审查分支、拉取远程基准分支，然后用 `origin/base...head` 三点 diff 计算变更，见 [code-review.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/code-review.js:228)。

`MR URL` 模式：第一个参数是 GitLab MR URL 时，本地不解析 MR diff，只上传 `mr_url`、workspace、user、cursor rules，让服务端处理 GitLab 数据，见 [code-review.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/code-review.js:452)。

**Git Diff 设计**
`GitUtils` 是本地 Git 数据采集层。它的关键设计是减少 Git 调用次数：用一次 `git diff --numstat --patch` 同时拿到行数统计和完整 patch，然后解析成：

```js
{
  file_path,
  diff_lines,
  diff
}
```

分支 diff 命令在 [git-utils.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/git-utils.js:151)，暂存区 diff 命令在 [git-utils.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/git-utils.js:273)。`--diff-filter=d` 会排除删除文件，这和 docs 里的设计文档一致。

**ibs:// 协议**
`lib/ibs-protocal.js` 是 macOS URL Scheme 注册器。它编译一个 AppleScript App 到 `~/Library/Application Support/IBSProtocol.app`，注册 `ibs://` 协议。浏览器点击 `ibs://cr?workspace=/path&session_id=xxx` 时，它会打开一个临时 `.command` 文件，在指定 workspace 下执行 `ibs cr --rerun=...`，见 [ibs-protocal.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/ibs-protocal.js:59)。文件名里 `protocal` 拼写错了，但不影响 require，除非外部约定期待 `protocol`。

**设计原理**
这个项目的设计核心不是“在 CLI 里完成 AI Review”，而是把本地最难获取的上下文可靠地交给服务端和 Cursor：

- 本地负责 Git、文件规则、工作区、用户、分支、commit、diff。
- 服务端负责 session、批次、去重、MR 模式数据获取和真正的审查上下文管理。
- Cursor 负责执行最终工具调用和展示交互结果。
- Git hooks 负责把 review 前置到 push/commit 流程里，但不强制阻断。

这种设计的好处是 CLI 轻量、后端可集中演进规则、Cursor 负责 AI 执行环境；代价是强依赖网络、后端 API、Cursor deep link、Git 命令和 shell 环境。

**明显风险和坑**
有一个实现不一致：`getDiffFileList()` 和 `getStagedDiffFileList()` 中，前面的文件 diff 会 gzip+base64，但最后一个文件保存时没有调用 `compressContent()`，见 [git-utils.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/git-utils.js:251) 和 [git-utils.js](/Users/zhuangbing.cai/Library/Containers/com.tencent.xinWeChat/Data/Library/Application%20Support/com.tencent.xinWeChat/2.0b4.0.9/fa45616b7194f791e5209ac4992d0bbd/Message/MessageTemp/9e20f478899dc29eb19741386f9343c8/File/ibs-cli/lib/git-utils.js:359)。如果后端统一按压缩格式解码，最后一个文件可能异常。

另一个坑是 README 和 hook 注释里提到 `git push --no-cr`，但 Git 原生命令不会接受这种自定义参数；实际代码检查的是 `IBS_NO_CR=1` 或 `IBS_NO_CR=true`。

还有几个工程风险：分支名和路径被拼进 shell 命令，存在特殊字符导致命令失败甚至注入风险；全局 hooks 会覆盖用户已有 `core.hooksPath`；当前没有测试脚本，`npm` 在我这个环境里也不可用，所以没有可执行的自动化验证闭环。

**总结**
这个项目本质上是 Shopee 内部 CR Shift-Left 的本地入口。它把“开发者 push 或手动执行命令”转换成“采集 Git diff 和规则、创建后端审查 session、让 Cursor 调用指定审查工具”。代码结构不大，但跨了 Git、npm lifecycle、Cursor deep link、macOS URL Scheme、后端 API、shell hook 多个边界，所以真正复杂的地方不在算法，而在这些系统边界的兼容性和失败兜底。
