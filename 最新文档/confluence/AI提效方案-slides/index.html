02 / Problem

当前 AI 使用最大瓶颈：个人会用，但组织不可复用

如果没有任务契约、上下文、边界和验证，AI 越能动手，风险面也越大。

1

输入散

一句自然语言就开写，AI 需要猜需求、猜接口、猜组件和验收标准。

2

上下文散

PRD、TD、YAPI、组件文档靠人工复制，质量强依赖使用者经验。

3

闭环弱

缺少自动验证、失败回灌和经验沉淀，同类错误反复出现。

越权修改 字段错误 组件误用 不可编译 返工不可度量
结论：先让 AI 可交付，再谈规模化。

05 / Use cases

优先落地高 ROI 场景

先选高频、结构稳定、容易验证的场景，不要一开始追求全能 Agent。

P0 需求理解

P0 接口提效

P1 生码

基于模板生成列表页、详情页、表单页，并接入状态、接口和组件。

P1 CR / Review

检查潜在 bug、异常分支、越权修改、规范问题和 PR 风险说明。

06 / Task Spec

所有 AI 任务先进入结构化输入

Task Spec 的价值是减少猜测，让 Codex 可以先计划、再按边界执行、最后按标准验收。

task

任务名称、类型、目标路由、页面或模块范围。

sources

PRD、前端 TD、后端 TD、YAPI、设计稿、参考页面。

constraints

组件库、请求封装、状态管理、可编辑目录、禁止事项。

acceptance

页面行为、字段一致性、loading/empty/error、lint、typecheck、截图。

输入越明确，后续验证和复盘越可靠。

07 / Context engineering

上下文不是越多越好，而是按任务规约

Prompt 是工作台，不是仓库；长期规则、动态接口和组件文档应通过文件或工具进入上下文。

需求上下文

PRD、TD、验收标准、疑问点，摘要后注入。

接口上下文

YAPI、字段类型、请求方法、mock，工具查询生成。

代码上下文

目录结构、相似页面、工具函数，按相关性检索。

组件上下文

组件库 API、示例、规范，禁止编造不存在组件。

规范上下文

架构、权限、埋点、i18n，沉淀在 `AGENTS.md`。

验证上下文

lint、typecheck、test、截图结果，失败后回灌。

好的上下文管理，让 AI 像读过项目的同事。

08 / Tool gateway

工具能提效，也必须受控

让 AI 只能通过批准的工具行动，工具有 Schema、权限、边界和观测。

Repo Reader读取目录、文件、相似页面，只读且限制范围。
YAPI Tool查询接口，生成类型和请求方法。
Component Docs查询组件 API 和示例，减少组件误用。
Command Runner执行白名单命令，设置超时和日志。

安全边界

独立分支或 worktree、editable scope、禁止无批准依赖、高风险操作确认、关键调用留日志。

最小权限 命令白名单 超时 审计
执行边界清楚，AI 才能更放心地承担任务。

09 / Verification loop

没有验证，AI 只能靠自信；有验证，AI 才能靠反馈

验证结果必须进入下一轮上下文，而不是只作为最终说明。

format
lint
typecheck
unit test
build
screenshot
CR rules

可确定问题

自动修复 1-2 轮，例如类型错误、字段不匹配。

不确定问题

停止并输出问题，例如需求冲突、信息缺失。

高风险问题

请求人工确认，例如公共模块、依赖和权限变更。

闭环原则：生成代码 -> 验证失败 -> 注入错误 -> 修复 -> 再验证。

10 / MVP

第一版 MVP：基于模板生成列表页

列表页高频、结构稳定、验证明确，是最适合跑通 Harness 闭环的入口场景。

1 个场景

先稳定一个列表页闭环，再扩展详情页、表单页、弹窗和批量操作。

输入PRD、TD、YAPI、模板目录、目标路由、验收标准。
执行找相似页面，生成类型和请求方法，接入筛选、表格、分页。
验证lint、typecheck、截图、字段一致性和 CR rules。
输出工程 Diff、验证结果、风险提示、经验沉淀建议。
MVP 不追求覆盖所有页面，只追求一个场景稳定交付。

11 / Team workflow

团队协作方式：人定义边界，AI 执行闭环

人不需要逐行指挥 AI，但必须定义目标、边界、风险和验收标准。

1

研发提交 Task Spec，并提供必要 PRD、TD、YAPI。

2

Codex 先 Plan，列出文件计划、接口计划和验证计划。

3

AI 在 editable scope 内改码，并自动跑验证。

4

失败自动修复或停止上报，完成后输出交付报告。

沉淀动作

如果同类问题出现第二次，就更新规则、模板、Skill、CR 检查项或组件示例。

AGENTS.md Skill 模板 FAQ CR rules
成熟度问题：团队是否还在反复教 AI 同一件事。

12 / Roadmap

建设路线：从个人标准化到规模化 Harness

不要先造大平台，先把一个闭环跑稳，再把稳定部分产品化。

P0 个人标准化

1-2 周：`AGENTS.md`、`config.toml`、Task Spec、Prompt 模板、Review 标准。

P1 最小闭环

2-4 周：列表页生码，接入 YAPI、组件文档、相似页面和自动验证。

P2 团队可控化

1-2 个月：工具网关、文件边界、命令白名单、CR Shift-Left、截图 QA。

P3 规模化

2-3 个月：Skills、Automations、评测集、质量指标、历史失败记忆。

节奏建议：先窄场景闭环，再横向扩展任务类型。

13 / Metrics

衡量 AI 提效，要看工程结果而不是代码行数

指标应该反向驱动 Harness 迭代：哪里失败，就补哪里上下文、工具、规则或验证。

效率指标

需求理解耗时、平均交付时长、人工返工次数、自动修复成功率。

质量指标

首次生成可编译率、PR Review 问题数、接口字段错误数、测试失败率。

治理指标

越权修改次数、命令失败率、工具调用失败率、成本和 Token 消耗。

沉淀指标

同类问题复发率、规则更新数、模板复用数、Skill 命中率。

最重要的指标：同类问题复发率。

如果同一个坑反复出现，说明它还没有被 Harness 化。

14 / First month

首月行动：先把闭环跑起来

从低成本的文档、规则和真实任务试点开始，边用边沉淀。

1

第一周

整理 `AGENTS.md`、`code_review.md`、Task Spec 模板和 3 个高频 AI 场景。

2

第二周

试点 3-5 个真实任务，记录返工点、验证结果和重复问题。

3

第三到四周

选择列表页生码，接入 YAPI、组件文档和 lint/typecheck 验证。

让 AI 在清晰边界、充足上下文和自动验证里稳定交付。

最终目标：任务标准化、上下文自动化、验证闭环化、经验资产化。
