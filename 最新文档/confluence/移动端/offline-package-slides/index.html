Overview

先抓住三条主线

这个项目不是单点优化，而是一套覆盖构建、运行、发布、回滚和多端研发的工程体系。

资源离线包闭环

Vite/Webpack 产物被改写、复制、校验、压缩，再由 APP 下载并在 WebView 请求时命中本地。

版本多应用治理

从一个 APP 一个 app_id，演进到 biz_id 下多个业务 app_id，支持独立发布、灰度和回滚。

研发PC/H5 双端

页面和业务逻辑共用，端侧差异落到 adapter/isolate，由构建时 alias 决定最终使用哪端实现。

最重要的心智模型：离线包解决“资源怎么到本地”，版本服务解决“用哪个版本”，双端架构解决“同一业务怎么在 PC/H5 运行”。
02
Background

为什么 Management APP 需要离线包

Management APP 是 Hybrid 模式：Native APP 内打开 H5。弱网下，纯在线资源会拖慢首屏甚至直接失败。

弱网
东南亚等网络环境下，HTML、JS、CSS、图片每次在线拉取都不稳定。
首屏
APP 打开 H5 页面的等待时间直接影响站点操作效率和用户感知。
兜底
本地资源命中失败还能回落 CDN/ALB，不把可用性压在单一路径上。
离线包的本质：把静态资源提前下载到 APP 本地，让 WebView 打开页面时少依赖网络。
03
Offline v1

早期方案：一个 APP，一个离线包应用

资源按更新频率拆成 vendor 和 bundle，但版本粒度仍然是整个 APP。

APP / app_id
例如 managementApp
v1
vendor.zip
React、MobX、ECharts、UI 库等低频资源
稳定
bundle.zip
业务 JS、HTML、图片、语言资源等高频资源
高频
  • 资源 URL 只需要带 _offl_id，APP 根据它找到 vendor 或 bundle。
  • 优点是实现成本低、APP 请求映射简单、BFF 版本模型也简单。
  • 问题是任意业务改动都要发布整个 APP 离线包，灰度和回滚粒度过粗。
  • 业务越来越多后，包体积、并行发布、跨业务互相阻塞都会变成瓶颈。
/mgmt/assets/app.js?_offl_id=bundle /mgmt/vendor/react.js?_offl_id=vendor

Build Output

离线包最终交给 APP 的是什么

不是把 dist 原样塞给 APP，而是生成可下载、可校验、可版本化的 zip 与 manifest。

zip 内部
vendor.zip verify.json deo.shopeemobile.com/... bundle.zip verify.json spx.test.shopee.sg/mgmt/... assets/...
offline_manifest.json
{ "packages": [ { "id": "vendor", "md5": "zip md5", "CDN": "https://.../vendor.zip" }, { "id": "bundle", "md5": "zip md5", "CDN": "https://.../bundle.zip" } ] }
verify.json 校验单文件，manifest 校验 zip 与下载地址；两层校验共同保证 APP 本地资源可靠。

Runtime

APP 如何把网络请求变成本地文件

离线包不是 H5 自己加载本地文件，而是 Native APP 拦截 WebView 请求并映射。

01
拉版本配置
冷启动或定时向 BFF/Version Service 获取版本。
02
下载 zip
比较 md5，缺失或变化才下载。
03
解压校验
zip md5 + verify.json 单文件校验。
04
拦截请求
读取 _app_id 和 _offl_id，定位本地目录。
05
失败兜底
本地缺失、校验失败或路径不匹配时走线上。
关键点：APP 优先用本地缓存配置，再异步拉最新配置，所以离线包发布后并不是全量用户立即生效。

HTML Mapping

为什么 offline-config 里列了大量路由

SPA 页面虽然共用 index.html，但 APP 是按真实 URL 路径找本地 HTML。

  • 用户可能打开 /mgmt/main/operation/fm-hub 这样的深层路径。
  • 这些路径在 Web 服务上都应返回同一个 SPA HTML。
  • 离线包里必须把同一个 HTML 复制到这些请求路径下，APP 才能命中本地。
  • 新增页面只改路由不补 offline-config，会导致离线包找不到 HTML，直接回落线上。

08
Offline v2

多应用离线包：biz_id 管 APP，app_id 管业务

版本粒度从“整个 APP”细化到“APP 内某个业务”。

旧模型
app_id = spx-mgmt-app version 100 vendor.zip bundle.zip

所有业务共享一个版本；一个业务异常可能影响整包灰度和回滚。

新模型
biz_id = spx-mgmt-app app_id = main app_id = order-tracking app_id = tools

每个业务 app_id 独立版本；发布、灰度、回滚粒度都更细。

react.js?_app_id=order-tracking&_offl_id=vendor page.js?_app_id=order-tracking&_offl_id=bundle

Pilot

Order Tracking：多应用拆分试点

目标是把高频独立业务从 main 中拆出去，同时保证旧路径和新 APP 迁移期不出事故。

关注点 旧状态 迁移策略
路径 /mgmt/order-tracking.html
/mgmt/order-detail.html		 兼容旧 .html，同时引导到新路由 /mgmt/order-tracking。
构建 业务在 main 包中，影响主包体积。 独立服务和 ALB；迁移期 main 只克隆 HTML 入口，不把完整业务资源打回主包。
发布 跟 main 绑定。 BFF/Version Service → FE → APP；先发版再改 Apollo 路由，避免 404。
回滚 整包回滚。 新版 APP 不可直接回旧协议；灰度问题回当前架构全量稳定包。

11
Gray & Update

灰度与即时更新：从“设备”转向“用户”

离线包长期停留在旧版本会影响新功能覆盖，也会增加后端多版本兼容成本。

灰度匹配
  • 旧方案按 device_id，难以精准命中目标用户。
  • 新方案支持 user_id，同时保留区域、内部灰度等维度。
  • PC version-mgr 会按用户 hash 和 region 选择 remoteEntry。
即时更新取舍
  • WebSocket/SSE 实时性高，但长连接维护成本高。
  • 轮询简单，但低频版本更新会产生大量无效请求。
  • 最终倾向业务场景检测 + APP 10 分钟定时检测兜底。
核心目标不是“秒级推送”，而是让关键版本能在可控时间内覆盖，同时避免升级机制打断现场操作。
12
Upgrade UX

升级体验：从强弹窗走向弱提醒

用户反馈频繁重启弹窗影响使用，因此升级策略要在覆盖时效与操作体验之间平衡。

强弹窗重启

覆盖快，实现简单；但强打断，用户体验最差。

中弹窗刷新

不用重启；但 WebView 运行态清理和稳定性成本高。

弱红点升级

不打断操作；覆盖时效较慢，版本碎片化更明显。

隐切后台刷新

用户感知弱；但触发时机不稳定，覆盖不可控。

jsBridge.checkUpgradeInfo() -> FeatureBadge.refreshBadgeStatus() -> jsBridge.syncBadges({ badges: [...] })
13
Rollback

回滚与降级：协议兼容是边界

离线包回滚看似只改版本配置，实际取决于 APP 是否能识别这套协议和本地是否已有旧资源。

普通全量回滚

将 live version 指回上一个稳定版本；APP 后续拉配置后切回旧资源。

灰度问题

停止灰度名单或把 gray version 指向稳定版本，不影响非灰度用户。

架构切换期

新版 APP 不支持旧单应用协议时，不能简单回旧包，只能发兼容修复或引导升级。

快速降级成立的四个前提：版本服务可切、APP 能及时拉、旧包可用、新旧协议兼容。
14
version-mgr SDK

SDK 化：把离线包和 PC 版本能力抽出来

WMS 已使用 `@scfe-common/version-mgr`，main 仍保留一份本地插件实现。

1自动 _app_id

传入 appId 后，资源 URL 默认带 _app_id 与 _offl_id。

2构建环境入 manifest

把 PFB、ENV、GIT_COMMIT、GIT_TAG、PIPELINE_URL 写入 envs，便于通知和追溯。

3独立静态资源包

i18n 等可拆成 static app_id，单独创建版本和刷新。

buildOfflinePlugin({ appId: 'sbs-mgmt-h5-dashboard', staticAppId: 'sbs-mgmt-h5-assets', enableIndependentStatic: true })
15
Dual End

双端适配：共用业务，隔离端差异

目标不是所有代码完全一样，而是让页面、模型、API 口径尽量统一，差异沉到边界层。

框架/路由层
端侧入口、路由、Vite/Webpack、离线包构建、PC remoteEntry。
pages 层
页面组合业务，不直接散落 PC/H5 差异。
applications 层
稳定业务出口，组合通用组件、hooks、rules、handlers。
isolate 适配层
同名接口，分别实现 index.h5 与 index.pc，把组件、跳转、布局、帮助弹窗等差异隐藏起来。
Service/API 层
与 BFF 通信，尽量不感知端差异，保证数据口径一致。
16
Adapter

同一行 import，构建器决定拿哪端实现

业务代码依赖 `@adapter/*` 或 `@applications/*`，H5/PC 通过 tsconfig 或 alias 指向不同文件。

业务代码
import { useNavigate } from '@adapter/hooks' import { getMultiEndProps } from '@adapter/rules' import { Link } from '@applications/components'

页面不需要知道当前是 PC 还是 H5。

构建映射
H5: @adapter/rules -> isolate/rules/index.h5 PC: @adapter/rules -> isolate/rules/index.pc

端侧组件、跳转、路由前缀、用户来源都在 isolate 内解决。

getMultiEndProps(h5Value, pcValue) // H5 返回 h5Value；PC 返回 pcValue
17
WMS / SBS

WMS：双端入口 + version-mgr 落地样板

WMS 包里同时能看到 H5 离线包、PC 版本管理、双端 adapter 和独立静态资源包。

H5 入口

wms-mgmt/h5/index.tsx
BrowserRouter、JSBridge、离线信息、翻译刷新、预加载事件。

PC 入口

wms-mgmt/pc/index.tsx
加载 PC 语言资源，并由 version-mgr 注入 remote entry 选择逻辑。

适配层

@wms-adapter/*
H5 默认指向 index.h5，PC Vite alias 改到 index.pc。

WMS 的 i18n 可以成为独立静态 app_id，APP 通过 `offlineResourceRefresh` 通知 H5 重新加载翻译，而不必刷新整包业务。

PC / FMS

PC Dashboard：remoteEntry 是版本入口

FMS 基座加载 remoteEntry，拿到子应用 routes，再把页面注册到 PC 框架。

01
构建 remoteEntry

重命名入口

FMS 异步化结论

  • 把灰度版本匹配强行迁入 Dashboard 内部风险大。
  • 原因是会绕开 Module Federation 共享机制，Shared、VueStore 等都要重新注入。

Debug Checklist

离线包问题优先查这几件事

大多数问题都落在路径、参数、版本配置、校验和协议兼容这几类。

现象 优先检查 常见修复
页面走线上 HTML 路径是否在 offline-config；URL 是否带 _app_id/_offl_id。 补 htmlOutDirs；跳转时保留离线参数。
资源 404 assetsPublicPath、ALB basePath、zip 内路径是否一致。 统一同域路径；重建 verify 与 manifest。
样式丢失 CSS 是否独立文件、路径是否被 APP 映射。 CSS 注入 JS；检查资源参数改写。
升级不生效 APP 是否拉到新版本、下载是否完成、是否需要二次打开。 checkUpgradeInfo、红点提示、主动 updateOfflinePkg。
回滚失败 新旧 APP 是否支持同一离线包协议。 在当前协议下发修复包，不跨协议直接回旧包。
