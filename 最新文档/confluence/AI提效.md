# AI 研发提效 Harness 方案

## 一句话结论

AI 提效的核心不是让大家多问 AI，也不是让 AI 更自由地写代码，而是把 AI 接进一个有任务契约、有上下文、有工具边界、有自动验证、有反馈沉淀的研发体系。

结合 Codex 最佳实践和 Harness 工程，可以把目标定义为：

```text
从一次性 AI 辅助
升级为
可控、可验证、可复用、可规模化的 AI 研发交付系统
```

换句话说：

```text
Codex 最佳实践解决“人如何稳定使用 Agent”
Harness 工程解决“组织如何让 Agent 稳定交付”
```

最终产物不应该只是几段代码，而应该是：

```text
工程 Diff + 验证报告 + 风险说明 + 经验沉淀
```

## 1. 当前问题

很多团队的 AI 提效停留在“个人会用”的阶段，常见问题是：

| 问题 | 现象 | 后果 |
| --- | --- | --- |
| 输入不结构化 | 一句“帮我做这个页面”就开始生成 | AI 猜需求、猜接口、猜组件 |
| 上下文靠人工复制 | PRD、TD、YAPI、组件文档散落各处 | 质量强依赖使用者经验 |
| 缺少工程边界 | AI 可以随意改文件、改公共模块、加依赖 | 容易引入隐性风险 |
| 缺少验证闭环 | 生成后不自动 lint、typecheck、test、截图 | 看起来完成，实际不可交付 |
| 失败不沉淀 | 同类错误反复出现 | 提效停留在一次性收益 |
| 缺少指标 | 只看“用了多少 AI”，不看返工率和成功率 | 无法判断是否真的提效 |

所以，AI 提效不能只建设 Prompt，而要建设一套最小 Harness。

## 2. 总体方案

方案分成两层：

### 第一层：Codex 使用体系

目标是让个人使用 AI 更稳定。

关键动作：

- 每个任务都写清 Goal、Context、Constraints、Done when。
- 复杂任务先 Plan，再实现。
- 仓库维护 `AGENTS.md`，沉淀项目规则和验证方式。
- 用 `config.toml` 固化模型、权限、MCP、profile 等默认配置。
- 每次重要改动都要求 Codex 跑验证并 review diff。
- 把稳定工作流沉淀成 Skill，把定期任务沉淀成 Automation。

### 第二层：研发 Harness 体系

目标是让组织能稳定复用 AI 交付能力。

核心链路：

```text
Task Spec
-> Context Collector
-> Plan
-> Controlled Execution
-> Verify
-> Feedback / Replan
-> Report
-> Memory
```

对应模块：

| 模块 | 职责 | 例子 |
| --- | --- | --- |
| Task Spec | 定义任务边界和验收标准 | PRD、TD、YAPI、目标路由、可编辑范围 |
| Context Collector | 自动收集任务上下文 | 仓库、相似页面、组件文档、接口文档 |
| Planner | 生成实施计划 | 文件计划、接口计划、组件计划、验证计划 |
| Tool Gateway | 管控工具调用 | YAPI、组件文档、命令执行、截图、CR |
| Sandbox | 限制执行边界 | worktree、editable scope、命令白名单 |
| Verifier | 自动验证结果 | lint、typecheck、test、build、screenshot |
| Feedback Loop | 失败后自动修复或重规划 | 类型错误修复、接口字段回查、组件用法修正 |
| Memory | 沉淀经验 | `AGENTS.md`、模板、Skill、CR 规则、FAQ |

## 3. 优先落地场景

不建议一开始做“全能 AI 平台”，应先从高频、结构稳定、容易验证的研发场景切入。

| 场景 | 主要价值 | 优先级 |
| --- | --- | --- |
| AI 辅助需求理解 | 从 PRD/TD 提取功能点、接口、权限、埋点、疑问点 | P0 |
| AI 接口提效 | 从 YAPI/Swagger 生成 TS 类型、请求方法、mock、字段映射 | P0 |
| AI 生码 | 基于模板生成列表页、详情页、表单页 | P1 |
| AI CR / Review | 检查潜在 bug、异常分支、越权修改、规范问题 | P1 |
| AI 测试提效 | 生成单测、组件测试、边界场景和失败日志分析 | P2 |
| AI 视觉与交互 QA | 截图检查空白、遮挡、溢出、loading/empty/error 状态 | P2 |
| AI Bug 排查 | 结合日志、堆栈、git diff 定位问题和修复建议 | P2 |
| AI 文档提效 | 生成技术方案、PR 描述、上线说明、回滚方案 | P2 |
| AI 重构迁移 | 组件库迁移、JS 到 TS、废弃 API 替换 | P3 |
| AI 性能分析 | 分析 bundle、重复依赖、首屏请求、Lighthouse 报告 | P3 |

第一阶段最推荐的 MVP 是：

```text
基于模板生成列表页
```

原因：

- 列表页模式稳定，适合做 Task Spec。
- 能覆盖 PRD、TD、YAPI、组件库、接口类型、页面状态等核心上下文。
- 验证方式明确：lint、typecheck、截图、字段校验。
- 成功后可扩展到详情页、表单页、弹窗和批量操作。

## 4. 标准 Task Spec

所有 AI 研发任务都应该先进入结构化输入，而不是直接一句自然语言开写。

推荐模板：

```yaml
task:
  name: 新增订单列表页
  type: page
  target_route: /order/list

sources:
  prd: xxx
  frontend_td: xxx
  backend_td: xxx
  yapi:
    - /api/order/list
    - /api/order/export

template:
  mode: existing_template
  source: src/pages/template/list-page

constraints:
  component_library: SSC UI React
  request_client: existing_request_wrapper
  state_management: existing_project_pattern
  editable_scope:
    - src/pages/order
    - src/services/order
  forbidden:
    - 不改公共请求封装
    - 不新增未批准依赖
    - 不修改无关页面

acceptance:
  - 页面能展示订单列表
  - 支持筛选、分页、导出
  - loading / empty / error 状态齐全
  - 接口字段与 YAPI 对齐
  - typecheck 通过
  - lint 通过
```

Task Spec 的价值是让 AI 少猜。

有了任务契约，Codex 才能先 Plan，再按边界执行，最后按验收标准验证。

## 5. Codex 工作流标准

每个 AI 任务建议按以下流程执行：

```text
1. 读取 Task Spec
2. 收集上下文
3. 生成计划
4. 人确认高风险计划
5. 受控修改代码
6. 自动验证
7. 失败自动修复 1-2 轮
8. 输出交付报告
9. 沉淀规则或模板
```

### Prompt 模板

```text
Goal:
- 我要实现/修复/重构什么。

Context:
- 相关 PRD、TD、YAPI、文件、相似页面、组件文档。

Constraints:
- 可编辑范围、禁止事项、依赖限制、团队规范。

Done when:
- 必须通过的验证命令、页面行为、人工验收点。
```

### `AGENTS.md` 建议内容

- 仓库结构和关键目录。
- 本地启动、构建、测试、lint、typecheck 命令。
- 组件库、请求封装、状态管理、路由、权限、埋点规范。
- AI 可编辑范围和禁止事项。
- PR 描述、Review、验证报告格式。
- 常见失败及处理方式。

### `config.toml` 建议内容

- 默认模型和 reasoning effort。
- sandbox mode 和 approval policy。
- 常用 profiles。
- MCP 工具配置，如 Jira、Confluence、YAPI、组件文档、GitHub。
- 项目级默认验证命令。

## 6. 上下文工程

AI 生码质量高度依赖上下文。上下文不是越多越好，而是要按任务类型做规约。

| 上下文 | 内容 | 注入方式 |
| --- | --- | --- |
| 需求上下文 | PRD、TD、验收标准、疑问点 | 摘要后注入 |
| 接口上下文 | YAPI、字段类型、请求方法、mock | 工具查询并生成类型 |
| 代码上下文 | 目录结构、相似页面、工具函数 | 自动检索相关文件 |
| 组件上下文 | 组件库文档、API、示例 | MCP 或本地文档查询 |
| 规范上下文 | 架构约束、权限、埋点、i18n | `AGENTS.md` 固化 |
| 验证上下文 | lint、typecheck、test、截图结果 | 每轮反馈注入 |

关键原则：

- Prompt 是工作台，不是仓库。
- 长期规则放 `AGENTS.md`，项目配置放 `config.toml`。
- 外部动态信息通过 MCP 或工具获取。
- 工具结果要结构化返回，而不是大段原始文本。
- 验证失败必须回灌给 Codex，用于下一轮修复。

## 7. 工具网关与安全边界

AI 能提效，是因为能使用工具；AI 会出风险，也往往是因为工具没有边界。

建议第一阶段建设这些工具能力：

| 工具 | 作用 | 控制点 |
| --- | --- | --- |
| Repo Reader | 读取目录、文件、相似页面 | 只读，限制最大文件数 |
| YAPI Tool | 查询接口并生成类型 | 校验字段和请求方法 |
| Component Docs | 查询组件用法和示例 | 禁止编造不存在组件 |
| Code Editor | 受控修改文件 | 限制 editable scope |
| Command Runner | 执行验证命令 | 命令白名单、超时 |
| Screenshot Tool | 截图和视觉检查 | 固定视口和状态 |
| CR Tool | 规则审查、安全审查 | 输出可定位问题 |
| Reporter | 生成交付报告 | 固定报告结构 |

安全边界：

- 每个任务使用独立分支或 worktree。
- 限制可编辑目录。
- 禁止改公共基础设施，除非任务明确允许。
- 禁止新增依赖，除非人工确认。
- 命令执行设置超时。
- 高风险操作需要人工确认。
- 关键工具调用保留日志，便于审计。

## 8. 自动验证与反馈闭环

没有验证，AI 只能靠自信；有验证，AI 才能靠反馈。

最小验证链路：

```text
format/lint -> typecheck -> unit test -> build -> screenshot -> CR rules
```

不同任务的必跑验证：

| 任务类型 | 必跑验证 |
| --- | --- |
| 接口/类型生成 | typecheck、字段一致性校验 |
| UI 页面 | lint、typecheck、截图 |
| 业务逻辑 | unit test、集成测试 |
| 路由/权限 | 权限规则检查、访问验证 |
| 公共组件 | unit test、storybook/截图、影响面分析 |
| 重构迁移 | 影响面分析、回归测试、CR rules |

反馈策略：

| 失败类型 | 处理方式 |
| --- | --- |
| 类型错误 | 注入错误日志，自动修复 |
| 接口字段不匹配 | 回查 YAPI，重新生成类型 |
| 组件 API 用错 | 查询组件文档，替换用法 |
| 测试失败 | 定位失败断言，修复业务逻辑 |
| 构建失败 | 判断路径、导出、依赖问题 |
| 需求不明确 | 暂停并向人提问 |
| 越权修改 | 停止并输出风险说明 |

推荐策略：

```text
可确定问题：自动修复 1-2 轮
不确定问题：停止并输出问题
高风险问题：请求人工确认
```

## 9. 交付报告

AI 任务完成后，应输出固定格式报告，避免“代码改完了但没人知道风险在哪里”。

推荐报告结构：

```text
变更摘要:
- 改了哪些文件，完成了哪些功能。

验证结果:
- 已运行哪些命令，结果如何。

风险说明:
- 可能影响哪些模块，哪些点需要人工确认。

未完成项:
- 哪些需求缺信息，哪些功能暂未覆盖。

经验沉淀:
- 是否需要更新 AGENTS.md、模板、Skill、CR 规则或 FAQ。
```

## 10. 路线图

### P0：个人提效标准化，1-2 周

目标：让团队稳定使用 Codex。

交付物：

- `AGENTS.md`
- `.codex/config.toml`
- `code_review.md`
- Task Spec 模板
- 标准 Prompt 模板
- AI 任务 checklist
- 需求理解、接口生成、CR、Bug 排查、文档生成等常用 Prompt

验收：

- 团队成员能按统一模板发起 AI 任务。
- 重要代码改动都能输出验证结果和风险说明。
- 常见规则不再靠口头重复解释。

### P1：最小 Harness 闭环，2-4 周

目标：让一个高频场景从输入到验证跑通。

建议场景：基于模板生成列表页。

能力：

- Task Spec。
- 自动读取 YAPI。
- 自动读取组件文档。
- 自动查找相似页面。
- 自动生成类型和请求方法。
- 自动生成页面代码。
- 自动跑 lint/typecheck。
- 失败后自动修复 1-2 轮。
- 输出交付报告。

验收：

- 首次生成可编译率提升。
- 人工返工次数下降。
- 接口字段错误减少。
- PR Review 问题数下降。

### P2：团队可控化，1-2 个月

目标：从个人工具变成团队可用工具。

能力：

- 工具网关。
- 文件编辑范围控制。
- 命令白名单。
- 高风险操作确认。
- worktree 隔离。
- 检查点和失败分类。
- CR Shift-Left。
- 截图 QA。

验收：

- AI 可以独立完成低风险任务闭环。
- 越权修改和无关改动可被拦截。
- 验证失败能自动修复或明确上报。

### P3：规模化 Harness，2-3 个月

目标：让稳定流程成为团队资产。

能力：

- 任务类型分类。
- 多模板体系。
- Codex Skills。
- Automations。
- 评测集。
- 质量指标面板。
- 历史失败记忆。
- 规则自动推荐。
- 多 Agent 协作。
- CI/CD 集成。

验收：

- 稳定场景可以批量复用。
- 同类问题复发率下降。
- 提效效果可用数据衡量。

## 11. 指标体系

不要只看“AI 写了多少代码”，应看端到端工程指标。

| 指标 | 含义 |
| --- | --- |
| 平均需求理解耗时 | PRD/TD 消化是否提效 |
| 首次生成可编译率 | 生码基础质量 |
| 自动修复成功率 | 反馈闭环能力 |
| PR Review 问题数 | 输出质量 |
| 接口字段错误数 | 接口上下文质量 |
| 人工返工次数 | 真实节省时间 |
| 越权修改次数 | 安全边界有效性 |
| 平均交付时长 | 端到端效率 |
| 平均 Token / 工具调用成本 | 成本可控性 |
| 同类问题复发率 | 经验是否沉淀 |

最重要的指标是：

```text
同类问题复发率
```

如果同一个坑反复出现，说明它还没有被规则化、模板化、Skill 化或检查项化。

## 12. 组织分工

| 角色 | 职责 |
| --- | --- |
| 研发 | 定义任务、确认计划、验收业务结果 |
| AI Owner | 维护 `AGENTS.md`、Prompt、Skill、模板和评测集 |
| 平台/工具同学 | 建设 MCP、工具网关、验证命令、截图能力 |
| Tech Lead | 定义规范、边界、Review 标准和风险策略 |
| QA | 提供测试用例、验收规则、视觉和交互检查标准 |

分工原则：

- 研发不应该每次重新教 AI 项目规则。
- AI Owner 负责把反复出现的经验沉淀成系统能力。
- 平台能力先服务高频窄场景，再逐步扩展。

## 13. 首月落地清单

第一周：

- 整理 `AGENTS.md`。
- 整理 `code_review.md`。
- 定义 Task Spec 模板。
- 梳理 3 个高频 AI 场景：需求理解、接口生成、CR。

第二周：

- 试点 3-5 个真实任务。
- 记录 AI 输出质量、返工点、验证结果。
- 把重复问题沉淀到 `AGENTS.md` 或 checklist。
- 形成第一版交付报告模板。

第三到四周：

- 选择一个列表页生码场景。
- 接入 YAPI 和组件文档上下文。
- 跑通 lint/typecheck 自动验证。
- 建立失败分类和自动修复策略。
- 统计首次可编译率、返工次数、Review 问题数。

## 14. 最终目标

AI 提效的成熟形态不是“每个人都很会问 AI”，而是：

```text
任务输入标准化
上下文获取自动化
工具执行受控化
质量验证自动化
失败反馈结构化
经验沉淀资产化
稳定流程规模化
```

一句话总结：

```text
让 AI 在清晰边界、充足上下文和自动验证里稳定交付。
```
