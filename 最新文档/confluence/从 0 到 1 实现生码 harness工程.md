# 从 0 到 1 实现生码 Harness 工程

## 核心判断

是的，现在很多「生码」本质上还是一头裸奔的野马：模型能力很强，但缺少约束、上下文、工具、校验和反馈。它可以跑得很快，但也容易跑偏、反复摔跤、写出看似正确但无法落地的代码。

Harness 工程要做的事情，不是立刻换一匹更强的马，也不是只把 Prompt 写长，而是逐步给它加上「马具」：

- 让它知道要去哪里：任务契约、输入规范、验收标准。
- 让它看清路况：PRD、TD、接口、模板、组件文档、代码上下文。
- 让它只能走安全路线：文件边界、权限、沙盒、工具网关。
- 让它每一步有反馈：lint、typecheck、测试、截图、CR 规则。
- 让它摔过一次后别再摔：失败归因、规则沉淀、模板升级、评测回流。

所以从 0 到 1 做生码 Harness，正确姿势不是一口气造大平台，而是先做一个最小闭环，然后按问题逐层加约束。

```text
裸奔生码 -> 有输入契约 -> 有上下文 -> 有工具 -> 有校验 -> 有反馈 -> 有记忆 -> 可规模化
```

## 生码 Harness 的目标

生码 Harness 的目标不是「让 AI 写代码」，而是「让 AI 在工程体系里交付代码」。

最终产物不应该只是几段代码片段，而应该是一个可验证的任务交付包：

- 代码改动。
- 接口类型。
- 页面/组件实现。
- 变更说明。
- 验证结果。
- 风险提示。
- 未完成项。
- 可复盘日志。

也就是说，生码的输出应该从「文本」升级为「工程 Diff + 验证报告」。

## 最小闭环

从 0 到 1 最重要的是先跑通这个闭环：

```text
任务输入 -> 上下文收集 -> 生成计划 -> 执行改码 -> 自动验证 -> 失败修复 -> 输出总结
```

对应到 Harness 的几个核心模块：

| 模块 | 作用 | 生码例子 |
| --- | --- | --- |
| Task Spec | 定义任务边界 | PRD、TD、YAPI、模板、验收标准 |
| Context Collector | 收集上下文 | 代码仓库、组件文档、接口文档、历史页面 |
| Planner | 生成实施计划 | 文件改动计划、接口接入计划、组件拆分 |
| Executor | 执行代码生成 | 创建页面、补类型、接接口、写状态逻辑 |
| Verifier | 自动验证 | lint、typecheck、test、build、截图 |
| Feedback Loop | 根据失败修复 | 编译失败修复、接口字段修复、组件用法修复 |
| Reporter | 输出结果 | 改了什么、如何验证、风险是什么 |

第一版 Harness 不需要很复杂，只要能把这条链路跑通，就已经从「裸奔」进入「可控」了。

## 第一层马具：任务输入契约

裸奔生码最常见的问题是：输入太散。人类给一句「帮我做一下这个页面」，Agent 就开始猜。猜需求、猜接口、猜组件、猜状态、猜交互，最后自然不稳定。

所以第一层马具是任务输入契约。每个生码任务都应该先被规整成一个结构化 Task Spec。

可以先用 Markdown 或 YAML，不必一开始做系统。

```yaml
task:
  name: 新增订单列表页
  type: page
  target_route: /order/list

sources:
  prd: xxx
  backend_td: xxx
  frontend_td: xxx
  yapi:
    - /api/order/list
    - /api/order/export

template:
  mode: existing_template
  source: src/pages/template/list-page

constraints:
  component_library: SSC UI React
  request_client: existing_request_wrapper
  state_management: existing_project_pattern
  editable_scope:
    - src/pages/order
    - src/services/order

acceptance:
  - 页面能展示订单列表
  - 支持筛选、分页、导出
  - 接口字段与 YAPI 对齐
  - typecheck 通过
  - lint 通过

forbidden:
  - 不改公共请求封装
  - 不新增未批准依赖
  - 不修改无关页面
```

有了 Task Spec，Agent 才知道任务边界。没有边界，就没有真正的工程交付。

## 第二层马具：上下文工程

生码质量高度依赖上下文。不是模型不会写，而是它不知道项目里「应该怎么写」。

上下文至少包括五类：

| 上下文 | 内容 | 作用 |
| --- | --- | --- |
| 需求上下文 | PRD、TD、验收标准 | 知道要做什么 |
| 接口上下文 | YAPI、字段类型、请求方法 | 知道数据从哪里来 |
| 代码上下文 | 目录结构、相似页面、工具函数 | 知道项目怎么组织 |
| 组件上下文 | 组件库文档、示例、API | 知道 UI 怎么拼 |
| 规范上下文 | 代码规范、权限、埋点、i18n | 知道边界和习惯 |

这里的关键不是「一次塞满」，而是做上下文规约：

- 当前任务必须注入什么。
- 相关文件按什么规则检索。
- 相似页面取几份。
- 长文档如何摘要。
- 接口文档如何转类型。
- 哪些规范永远放在 system / developer 级别。
- 哪些信息按需调用工具查询。

上下文管理做得好，Agent 会像一个读过项目的同事；上下文管理做得差，Agent 就像刚入职但没人带的实习生。

## 第三层马具：工具网关

Agent 真正能干活，是因为它能使用工具。但工具如果不受控，也会带来风险。

生码 Harness 至少需要这些工具：

| 工具 | 作用 |
| --- | --- |
| Repo Reader | 读取目录、文件、相似页面 |
| Component Docs | 查询组件库用法和示例 |
| YAPI Tool | 读取接口并生成类型和请求方法 |
| Code Editor | 受控修改文件 |
| Command Runner | 执行 lint、typecheck、test、build |
| Screenshot Tool | 页面截图和视觉验证 |
| CR Tool | 规则审查、安全审查、接口审查 |
| Reporter | 生成交付报告 |

工具网关要解决四件事：

- 工具有 Schema：参数必须结构化。
- 工具有权限：哪些任务能调用哪些工具。
- 工具有边界：哪些文件能读写，哪些命令能跑。
- 工具有观测：每次调用都能记录输入、输出、耗时和错误。

裸奔的 Agent 是「想干什么就干什么」。加了工具网关的 Agent 是「只能通过批准的工具干活」。

## 第四层马具：执行沙盒

生码一定会涉及写文件、跑命令、装依赖、调用接口，这些都需要边界。

从 0 到 1 可以先做轻量沙盒：

- 每个任务使用独立分支或 worktree。
- 限制可编辑目录。
- 禁止改公共基础设施，除非任务明确允许。
- 禁止新增依赖，除非人工确认。
- 命令执行有超时。
- 高风险命令需要人工确认。

进一步成熟后再加入：

- 容器级执行环境。
- 网络访问白名单。
- 密钥脱敏。
- 资源配额。
- 多租户隔离。

执行沙盒的目标不是限制 Agent 变弱，而是让它可以放心地变强。

## 第五层马具：自动验证

生码最关键的驯化手段是验证。没有验证，Agent 只能靠自信；有了验证，Agent 才能靠反馈。

最小验证集可以从这几项开始：

```text
format/lint -> typecheck -> unit test -> build -> screenshot -> CR rules
```

不同任务类型可以有不同验证策略：

| 任务类型 | 必跑验证 |
| --- | --- |
| 类型/接口生成 | typecheck、接口字段校验 |
| UI 页面 | lint、typecheck、截图 |
| 业务逻辑 | unit test、集成测试 |
| 路由/权限 | 权限规则检查、页面访问验证 |
| 公共组件 | unit test、storybook/截图、影响面分析 |

验证结果必须进入下一轮上下文，而不是只作为终态输出。

```text
生成代码 -> typecheck 失败 -> 注入错误 -> Agent 修复 -> 再验证
```

这才是 Harness 的闭环。

## 第六层马具：失败处理与重规划

Agent 一定会失败。工程系统的成熟度，不在于是否失败，而在于失败后怎么处理。

需要把失败分类：

| 失败类型 | 处理方式 |
| --- | --- |
| 类型错误 | 注入错误日志，自动修复 |
| 接口字段不匹配 | 回查 YAPI，重新生成类型 |
| 组件 API 用错 | 查询组件文档，替换用法 |
| 测试失败 | 定位失败断言，修复业务逻辑 |
| 构建失败 | 判断依赖/路径/导出问题 |
| 需求不明确 | 暂停并向人提问 |
| 越权修改 | 回滚该部分改动并上报 |

这里要避免两个极端：

- 不要一失败就问人，这样无法提效。
- 不要无限自动修，容易越修越偏。

比较合理的策略是：

```text
可确定问题：自动修 1-3 轮
不确定问题：停止并输出问题
高风险问题：请求人工确认
```

## 第七层马具：记忆与经验沉淀

真正的驯化，是让 Agent 下次少犯同类错误。

每次失败后都应该问：

```text
这个问题应该沉淀成什么？
```

可能的沉淀形式：

- 一条项目规则。
- 一个模板改进。
- 一个组件示例。
- 一个接口类型生成规则。
- 一个测试用例。
- 一个 CR 检查项。
- 一个 Prompt 约束。
- 一个工具能力。
- 一个 FAQ。

例如：

| 失败 | 沉淀 |
| --- | --- |
| 反复用错 Table 分页 API | 补组件示例和规则 |
| 接口字段大小写错 | YAPI 类型生成自动化 |
| 忘记权限判断 | 页面模板内置权限块 |
| 修改了无关文件 | 加 editable_scope 约束 |
| 漏掉 loading/error 状态 | 验收清单加页面状态规则 |

Harness 的核心理念就是：不要让模型在同一个坑里反复摔。

## 从 0 到 1 的迭代路线

### P0：人工辅助型

目标：让 Agent 按规范生成代码，但主要由人提供上下文。

能力：

- 任务模板。
- 固定 Prompt。
- 人工贴 PRD/TD/YAPI。
- Agent 改码。
- 人工跑验证。

价值：快速验证生码场景是否成立。

问题：上下文不稳定，强依赖使用者经验。

### P1：最小 Harness 闭环

目标：让 Agent 自动收集基本上下文，并能自动验证。

能力：

- Task Spec。
- 自动读取相似页面。
- 自动读取组件文档。
- 自动读取 YAPI。
- 自动生成类型和请求方法。
- 自动跑 lint/typecheck。
- 失败后自动修复 1-2 轮。
- 输出交付报告。

价值：从「会写」变成「能交付」。

### P2：可控生码平台

目标：让生码过程具备权限、边界、审计和可恢复能力。

能力：

- 工具网关。
- 文件编辑范围控制。
- 命令白名单。
- 高风险操作确认。
- 检查点。
- 任务状态机。
- 失败分类和重规划。
- CR Shift-Left。

价值：从个人效率工具变成团队可用工具。

### P3：规模化 Harness

目标：让系统能持续学习和规模化复制。

能力：

- 任务类型分类。
- 多模板体系。
- 评测集。
- 生码质量指标。
- 历史失败记忆。
- 规则自动推荐。
- 多 Agent 协作。
- CI/CD 集成。

价值：从「单次生码」升级成「研发生产线」。

## 生码 Harness 的推荐架构

```text
                     Task Spec
                         |
                         v
                Context Collector
      PRD / TD / YAPI / Repo / Components / Rules
                         |
                         v
                    Planner
             生成文件计划、接口计划、验证计划
                         |
                         v
                    Executor
              受控编辑代码、生成类型、接接口
                         |
                         v
                    Verifier
          lint / typecheck / test / build / screenshot / CR
                         |
              success ---+--- failed
                 |              |
                 v              v
              Report       Feedback + Replan
```

这套架构可以先用脚本、Prompt、MCP 工具和本地命令拼起来，不必一开始做完整平台。先把链路跑通，再把稳定部分产品化。

## MVP 可以怎么做

第一版可以只支持一种高频场景：基于模板生成列表页。

输入：

- PRD 链接。
- 后端 TD 链接。
- YAPI 接口。
- 页面模板目录。
- 目标路由。

流程：

1. 读取 Task Spec。
2. 拉取 PRD/TD/YAPI。
3. 找一个相似列表页。
4. 生成接口类型和请求方法。
5. 基于模板生成页面。
6. 自动接入筛选、表格、分页、loading、empty、error。
7. 跑 lint/typecheck。
8. 失败自动修复。
9. 输出变更说明和验证结果。

MVP 不追求覆盖所有页面，只追求一个场景稳定闭环。只要一个场景跑顺了，再扩展详情页、表单页、弹窗、批量操作等。

## 判断是否驯化成功

可以用这些指标判断 Harness 是否真的有效：

- 首次生成可编译率。
- 自动修复成功率。
- 人工返工次数。
- PR 审查问题数。
- 接口字段错误数。
- 平均交付时长。
- 平均 Token 成本。
- 工具调用失败率。
- 越权修改次数。
- 同类问题复发率。

最重要的是「同类问题复发率」。如果一个坑反复出现，说明还没有被 Harness 化。

## 一句话落地原则

从 0 到 1 做生码 Harness，不要追求一开始就做一个全能 Agent。

先让它在一个窄场景里做到：

```text
输入清楚、上下文充分、工具受控、执行安全、验证自动、失败可修、经验可沉淀
```

这时它才不再是裸奔的野马，而是开始具备工程交付能力的「可驯化生产力」。
