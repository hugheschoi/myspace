# Codex 最佳实践总结

## 文章信息

- 原文：[Best practices - Codex | OpenAI Developers](https://developers.openai.com/codex/learn/best-practices)
- 用户提供链接：[知乎专栏](https://zhuanlan.zhihu.com/p/1938967453951571269)（当前直接访问返回反爬/异常访问页，本文以可读取的官方原文和本地笔记为准）
- 主题：如何在 CLI、IDE extension、Codex app 中更稳定地使用 Codex。
- 阅读日期：2026-05-14

## 一句话结论

这篇文章的核心不是「怎么写一个更长的 Prompt」，而是：把 Codex 从一次性助手，升级为一个会被配置、被约束、被复盘、被自动化的工程队友。

```text
一次性提问 -> 任务上下文 -> 持久规则 -> 稳定配置 -> 验证评审 -> 外部工具 -> 复用技能 -> 自动化流程
```

## 核心主线

Codex 的效果不只取决于模型能力，也取决于使用者是否给了它正确的工作环境。文章建议先把任务说清楚，再把稳定有效的规则沉淀到 `AGENTS.md` 和 `config.toml`，随后通过测试、评审、MCP、Skills 和 Automations 把单次协作变成可重复的工程流程。

换句话说，Codex 不是只负责「生成代码」。在合适的上下文和工具下，它可以参与计划、实现、验证、复盘和自动化维护。

## 给看不懂者的导读

这篇文章容易看乱，是因为它表面上讲了很多功能：Prompt、Plan、`AGENTS.md`、配置、MCP、Skills、Automations、session controls。其实它们不是并列的技巧清单，而是同一条成熟路径上的不同层级。

可以把全文拆成四层来理解：

| 层级 | 解决的问题 | 对应能力 |
| --- | --- | --- |
| 单次任务说清楚 | 让 Codex 知道这次要做什么 | Prompt、Context、Done when |
| 长期规则沉淀 | 不要每次重复解释团队习惯 | `AGENTS.md`、`config.toml` |
| 外部上下文接入 | 不靠复制粘贴搬运信息 | MCP、Connectors |
| 稳定流程规模化 | 把重复工作产品化、自动化 | Skills、Automations、subagents |

所以全文真正想表达的是：不要只追求「这一句 Prompt 怎么写更神」，而要搭建一套让 Codex 稳定工作的环境。

读这篇文章时，可以抓住三个关键词：

- 可控：权限、沙盒、审批、任务边界要清楚。
- 可验证：测试、lint、typecheck、review 要进入完成标准。
- 可复用：反复有效的提示词、流程和规则要沉淀成文件、Skill 或 Automation。

如果你只想马上落地，先做这五件事：

1. 每次任务都写 Goal、Context、Constraints、Done when。
2. 复杂需求先让 Codex plan，不要直接开写。
3. 在仓库根目录维护一个短而真实的 `AGENTS.md`。
4. 把常用模型、权限、MCP 等放进 `config.toml`。
5. 让 Codex 每次重要改动都跑验证，并 review 自己的 diff。

一个可以直接套用的任务模板：

```text
Goal:
- 我要实现/修复/重构什么。

Context:
- 相关文件、接口文档、错误日志、可参考页面。

Constraints:
- 不要改哪些模块；不要新增哪些依赖；遵守哪些团队规范。

Done when:
- 哪些测试通过；哪个 bug 不再复现；哪些行为需要人工确认。
```

## 1. 第一次用好：任务上下文和 Prompt

文章认为，Codex 已经能处理很多不完美的 Prompt；但在大型仓库、高风险改动或复杂任务中，结构化上下文会显著提高可靠性。

一个默认好用的 Prompt 应包含四件事：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| Goal | 要改什么、建什么、修什么 | 新增订单列表页 |
| Context | 哪些文件、目录、文档、报错相关 | 参考现有列表页、YAPI、组件文档 |
| Constraints | 架构、规范、安全、权限、依赖限制 | 不新增依赖、不改公共请求封装 |
| Done when | 什么状态算完成 | typecheck 通过、bug 不再复现 |

这样做的价值是让 Codex 少猜、少跑偏，也让最终结果更容易 review。

文章还建议按任务难度选择 reasoning level：

- Low：快速、明确、范围小的任务。
- Medium / High：复杂改动、调试、跨文件分析。
- Extra High：长周期、多步骤、需要深度推理的任务。

## 2. 复杂任务先 Plan

对复杂、模糊、难描述的任务，文章建议先让 Codex 进入计划阶段。Plan Mode 的价值不是延迟编码，而是在动手前完成三件事：

- 收集足够的仓库上下文。
- 通过问题澄清真实意图。
- 形成可执行、可验证的实施计划。

如果需求还很粗，也可以让 Codex 先「采访」你：要求它挑战假设、追问边界，把模糊想法整理成具体任务，再开始写代码。

更高级的团队流程可以使用 `PLANS.md` 或 execution plan 模板，让长任务有固定的计划格式和检查点。

## 3. 用 `AGENTS.md` 沉淀可复用规则

当某种提示方式反复有效，就不应该每次手动重复，而应该沉淀到 `AGENTS.md`。

可以把 `AGENTS.md` 理解成给 agent 看的 README。它会自动进入上下文，适合存放仓库级、团队级的工作方式。

一个实用的 `AGENTS.md` 通常包括：

- 仓库结构和重要目录。
- 项目启动、构建、测试、lint 命令。
- 工程约定、PR 期望和 review 标准。
- 权限边界、不要做的事。
- 什么算完成，以及如何验证。

文章强调，`AGENTS.md` 不宜写成空泛长文。短、准、常更新，比长而笼统更有效。当 Codex 反复犯同一个错误，可以让它做一次复盘，然后把新的规则写回 `AGENTS.md`。

## 4. 用 `config.toml` 保持行为一致

配置是让 Codex 跨会话、跨入口表现一致的关键。文章建议的分层方式是：

- 个人默认值放在 `~/.codex/config.toml`。
- 仓库特定行为放在 `.codex/config.toml`。
- CLI 参数覆盖只用于临时场景。

`config.toml` 可以承载模型、reasoning effort、sandbox mode、approval policy、profiles、MCP、feature flags 等长期偏好。

尤其是权限相关配置，文章建议新手先保守：默认保持审批和沙盒较严格，等熟悉工作流和仓库可信度后，再为特定项目或任务放宽。

一个重要判断是：很多「Codex 质量问题」其实是环境问题，例如工作目录不对、写权限不足、模型默认值不合适、缺少必要工具或连接器。

## 5. 用测试和 review 提升可靠性

文章反复强调，不要停在「让 Codex 改完代码」。更稳的方式是让 Codex 一并完成验证闭环：

- 必要时新增或更新测试。
- 运行相关测试套件。
- 检查 lint、格式化、类型检查。
- 确认最终行为符合需求。
- 对 diff 做一次风险 review。

这意味着 Prompt 或 `AGENTS.md` 里要写清楚「好」的标准。比如项目应该跑哪些命令、哪些风险不能接受、哪些改动需要额外说明。

Codex app 的 diff 面板和 `/review` 命令可以用于本地评审，也可以结合团队的 `code_review.md` 让 review 行为保持一致。

## 6. 用 MCP 连接仓库外的上下文

当 Codex 需要的上下文不在代码仓库里，就适合使用 MCP。

MCP 的适用场景包括：

- 需要的信息在外部系统中。
- 数据变化频繁，不适合复制粘贴。
- 希望 Codex 调用工具，而不是依赖一次性文本说明。
- 希望跨用户或项目复用同一类集成。

常见例子包括 Jira、Confluence、Slack、GitHub、内部接口文档、监控平台等。文章也提醒，不要一开始就把所有工具都接入；先接入最能减少手工复制和重复查询的一两个工具，再逐步扩展。

## 7. 用 Skills 产品化重复工作

如果你反复复用同一段 Prompt，或者反复纠正同一种工作流，就应该考虑把它变成 Skill。

Skill 适合封装：

- 明确的使用场景。
- 固定输入和输出。
- 稳定的操作步骤。
- 必要的脚本、模板或资源。

文章建议每个 Skill 聚焦一个任务，不要一开始覆盖所有边界。先从 2 到 3 个真实 use case 起步，跑通后再迭代。

适合做成 Skill 的工作包括：

- 日志排查。
- 发布说明生成。
- PR checklist review。
- 迁移计划。
- 监控或事故摘要。
- 标准化调试流程。

## 8. 用 Automations 自动执行稳定流程

当一个流程已经手动跑稳，就可以进一步交给 Automations 定时运行。

文章给出的候选场景包括：

- 汇总近期 commits。
- 扫描潜在 bug。
- 起草 release notes。
- 检查 CI 失败。
- 生成站会摘要。
- 周期性运行分析任务。

一个很好的分工是：Skills 定义方法，Automations 定义时间。还不稳定、还需要频繁人工指导的流程，应该先做成 Skill 并迭代稳定，再自动化。

## 9. 管理长会话：一个任务一条线程

Codex 的 session 不只是聊天记录，而是累积上下文、决策和操作的工作线程。线程管理会直接影响质量。

文章建议一个清晰原则：一个 coherent unit of work 对应一条线程。也就是说，一个任务一条线程，而不是一个项目永远只用一条线程。

常见会话控制能力包括：

- `/resume`：恢复历史会话。
- `/fork`：保留原上下文并分叉新方向。
- `/compact`：在上下文变长时压缩历史。
- `/agent`：在并行 agent 线程之间切换。
- `/status`：查看当前会话状态。

对于可并行拆分的工作，可以用 subagents 承担探索、测试、triage 等边界清楚的任务，让主线程保持在核心问题上。

## 常见误区

文章最后列出了一组非常实用的反模式，可以归纳为下面几类：

| 误区 | 更好的做法 |
| --- | --- |
| 把长期规则塞进每次 Prompt | 沉淀到 `AGENTS.md` 或 Skill |
| 不告诉 Codex 怎么验证 | 写清测试、构建、lint、review 命令 |
| 复杂任务直接开写 | 先 Plan，再实现 |
| 过早放开全部权限 | 默认保守，按可信场景逐步放宽 |
| 多个实时线程改同一批文件 | 使用 git worktree 或明确分工 |
| 手动还不稳定就自动化 | 先 Skill 化，再 Automation |
| 一直盯着 agent 每一步 | 把它当并行队友，自己也继续推进 |
| 一个项目只用一条长线程 | 一个任务一条线程，避免上下文膨胀 |

## 落地清单

### 个人使用者

- 为每个任务写清 Goal、Context、Constraints、Done when。
- 复杂任务先用 Plan Mode。
- 用 `/init` 初始化 `AGENTS.md`，再删掉空泛规则。
- 在 `~/.codex/config.toml` 里放个人默认配置。
- 每次重要改动都要求 Codex 运行验证并 review diff。

### 团队使用者

- 仓库根目录维护共享 `AGENTS.md`。
- 把 review 标准沉淀成 `code_review.md` 并在 `AGENTS.md` 中引用。
- 为常见任务建立 Skills，例如 PR review、接口迁移、release notes。
- 只接入能显著减少人工复制的 MCP。
- 对稳定流程再上 Automations。

### 组织级演进

- 把「一次性生码」升级为「任务输入 -> 计划 -> 实现 -> 验证 -> review -> 复盘」闭环。
- 把重复 Prompt 变成规则或 Skill。
- 把稳定 Skill 变成 Automation。
- 把失败复盘转化为新的 `AGENTS.md`、Skill 或配置更新。

## 我的理解

这篇文章真正有价值的地方，是把 Codex 的最佳实践从「提示词技巧」提升到了「工程系统建设」。

Prompt 只是入口，真正决定长期效果的是：

- 上下文是否准确。
- 规则是否可复用。
- 权限是否可控。
- 验证是否自动化。
- 外部信息是否能通过工具获得。
- 重复流程是否能沉淀成 Skill 或 Automation。
- 每次失败是否能反哺下一次协作。

所以，使用 Codex 的成熟度可以用一句话衡量：

```text
你是否还在每次重新解释工作方式，还是已经把工作方式写进了系统？
```
