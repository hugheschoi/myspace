01 / Core idea

Codex 的关键不是一次问答，而是持续配置和改进

成熟用法是把 Codex 当作工程队友：给它上下文、规则、权限边界、验证方式和可复用工具。

AGENTS.md
config.toml
测试评审
MCP / Skills
Automation
核心主线：从一次性提示，走向可复用的工程系统。

03 / Prompt

第一次用好：给 Codex 四块任务上下文

Prompt 不必完美，但在大型仓库和高风险任务中，结构化上下文会显著减少猜测。

1

Goal

要修什么、建什么、改变什么行为。

2

Context

相关文件、目录、文档、报错和可参考实现。

3

Constraints

架构规范、安全边界、依赖限制和团队约定。

4

Done when

测试通过、行为改变、缺陷不再复现等完成标准。

少猜测 更聚焦 更容易 review 更适合复杂仓库
提示词重点：说清目标、上下文、约束和验收。

04 / Reasoning level

按任务难度选择推理强度

不同任务需要不同的思考深度。速度和可靠性之间，可以按任务风险做选择。

Low

适合小范围、目标明确、低风险任务。追求快速反馈。

Medium

适合常规开发和局部调试。兼顾速度与分析。

High

适合跨文件变更、复杂 bug、需要综合上下文的任务。

Extra High

适合长周期、多步骤、agentic、推理密集型任务。

实践原则：任务越复杂，越要用更强计划和验证闭环。

05 / Plan first

复杂任务先 Plan，再编码

Plan Mode 的价值是把模糊任务变成可执行、可验证的工程计划。

先想清

复杂、模糊、跨模块任务，不要急着改代码。先让 Codex 收集上下文、追问边界、拆解路径。

Plan Mode 适合大多数复杂任务，让 Codex 先探索、澄清、形成计划。
Interview 需求还不清楚时，让 Codex 先采访你并挑战假设。
PLANS.md 团队可为长任务约定固定计划模板和执行检查点。
适用场景：复杂、模糊、高风险、难以一次说明白的任务。

06 / AGENTS.md

把有效提示沉淀成 `AGENTS.md`

当一种提示方式反复有效，就不该每次手动重复。让仓库自己携带 agent 工作规则。

项目怎么跑

目录结构、启动方式、构建、测试、lint、typecheck 命令。

代码怎么写

工程约定、PR 期望、架构边界、review checklist。

什么不要做

权限限制、依赖限制、禁止改动范围、验收标准。

短、准、真实的 `AGENTS.md`，比长而空泛的规则更有用。

当 Codex 同类错误出现第二次，就把复盘结论沉淀成规则。

07 / Configuration

用 `config.toml` 让行为跨会话一致

很多质量问题其实是环境问题：目录、权限、模型默认值、工具和连接器没有配好。

个人默认 `~/.codex/config.toml` 放个人偏好和常用配置。
仓库规则 `.codex/config.toml` 放项目专属行为和工具配置。
临时覆盖 CLI 参数只用于一次性任务，不替代长期配置。

配置维度

model、reasoning effort、sandbox mode、approval policy、profiles、MCP、feature flags。

默认保守 按需放宽 可信仓库 可复现
权限建议：新手先严格，熟悉工作流后再为可信项目放宽。

08 / Reliability

不要只让 Codex 改代码，也要让它验证和 review

Prompt 或 `AGENTS.md` 要写清楚什么叫“好”，Codex 才能完成可靠闭环。

✓

为变更补充或更新必要测试。

✓

运行相关测试套件，必要时补跑构建、lint、格式化和类型检查。

✓

确认最终行为与请求一致，而不只是代码能编译。

✓

对 diff 做一次 bug、回归和风险模式 review。

✓

把团队 review 标准写进 `code_review.md`，再从 `AGENTS.md` 引用。

Codex 不只生成代码，也能参与测试、检查和评审。

09 / MCP

用 MCP 连接仓库外的动态上下文

当上下文在外部系统里，复制粘贴就会变成瓶颈。MCP 让 Codex 直接使用工具。

什么时候用 MCP

信息不在仓库里、变化频繁、需要可重复集成，或希望 Codex 调工具而不是读一次性文本。

Jira Confluence GitHub Slack YAPI

怎么接入更稳

不要一开始接满所有工具。先选一两个能消除手工复制、重复查询的工具，再根据真实摩擦扩展。

少而准 可复用 可授权 可审计
文章提到 Codex 支持 STDIO 和 Streamable HTTP MCP servers with OAuth。

10 / Skills

把重复工作产品化为 Skills

如果你反复复用同一段 Prompt，或反复纠正同一流程，就该考虑写成 Skill。

一个 Skill，一个任务

从 2 到 3 个真实 use case 起步。

定义输入输出

让触发场景、产物和边界清楚。

必要时加脚本

只有能提升可靠性时才加入资产或脚本。

日志排查 发布说明 PR review 迁移计划 事故摘要 标准调试流

Skills 是把“我总是这样做”变成“系统默认会这样做”。

Skill 先本地迭代，稳定后再作为 plugin 分享给团队。

11 / Automations

稳定流程再自动化

Automations 适合已经手动跑稳的流程。方法先稳定，时间表再自动。

Skill

定义做事方法：步骤、输入、输出、质量标准。

Commit 摘要 定期汇总近期代码变化，辅助周报和站会。
Bug 扫描 周期性检查潜在风险、CI 失败和回归模式。
Release notes 根据稳定规则起草发布说明和变更摘要。
Skills 定义方法 Automations 定义节奏 先可靠，再定时
还需要大量人工指导的流程，应先 Skill 化并迭代。

12 / Session controls

一个任务一条线程，保持上下文干净

Session 是累积上下文、决策和操作的工作线程。线程管理会直接影响输出质量。

1

同一问题留在同一线程

保留推理轨迹和已做决策，减少重复解释。

2

真正分叉才 fork

方向变化明显时，用 `/fork` 保留原始上下文。

3

长线程及时 compact

上下文膨胀时压缩历史，避免旧噪音拖累新任务。

/resume /fork /compact /agent /status subagents
关键原则：不要一个项目一条超长线程，而是一个任务一条线程。

13 / Anti-patterns

常见错误：把工程系统问题当成提示词问题

文章最后的反模式，基本都指向同一件事：没有把有效做法沉淀下来。

把长期规则塞进每次 Prompt，而不是写入 `AGENTS.md` 或 Skill。

不给 Codex 构建、测试、lint、review 的执行方式。

复杂任务跳过计划，直接让 agent 开始改代码。

还没理解工作流，就给整台电脑完整权限。

多个实时线程同时改同一批文件，却不使用 worktree。

手动流程还不可靠，就过早变成 Automation。

把 Codex 当作需要逐步盯着看的工具，而不是并行队友。

一个项目只用一条长线程，导致上下文越来越膨胀。

反模式的共同解法：规则沉淀、权限收敛、验证明确、线程切分。

14 / Prompt template

马上可用：把任务写成四段

这不是为了把 Prompt 写长，而是让 Codex 知道边界、依据和验收方式。

Goal

我要实现、修复或重构什么；希望最终行为发生什么变化。

Context

相关文件、接口文档、错误日志、截图、现有页面、可参考实现。

Constraints

不要改哪些模块；不要新增哪些依赖；必须遵守哪些团队规范。

Done when

哪些测试通过；哪个缺陷不再复现；哪些结果需要人工确认。

少解释一次 少返工一次 更容易验收 更容易复盘
最小落地动作：从下一次任务开始，用这四段发给 Codex。

15 / Roadmap

落地路线图：从个人习惯到团队系统

不要一口气追求大而全。先让单次协作稳定，再逐层沉淀。

1. 写清任务

每次任务都有 Goal、Context、Constraints、Done when。

2. 固化规则

把常用约定写进 `AGENTS.md` 和 `config.toml`。

3. 建立闭环

让 Codex 执行测试、检查、review，并输出验证结果。

4. 规模化

用 MCP、Skills、Automations 把稳定流程复用到团队。

成熟度问题：你是否还在每次解释工作方式，还是已经把工作方式写进系统？
