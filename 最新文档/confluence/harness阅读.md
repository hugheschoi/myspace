# 《理解 Harness Engineering》深度解读

原文：<https://developer.volcengine.com/articles/7628804506616905778>  
关联背景：OpenAI 的 Codex agent-first 工程实验：<https://openai.com/zh-Hans-CN/index/harness-engineering/>

## 一句话总结

Harness Engineering 不是又一个提示词技巧，而是把「模型能思考」变成「系统能稳定交付」的一整套工程基础设施：上下文、工具、权限、沙盒、状态、评测、反馈、成本和治理，都属于 Harness。

换句话说：

```text
Agent = Model + Harness
```

模型提供推理能力，Harness 提供工作环境和行为边界。真正决定 Agent 能否进入生产环境的，往往不是模型单次回答有多聪明，而是这套外部系统能不能让它少犯错、可恢复、可审计、可持续改进。

## 文章主旨

这篇文章想解决的问题是：当 AI Agent 不再只是回答问题，而是能读代码、改代码、调接口、跑命令、开 PR、做审查、甚至长时间自主执行任务时，工程师应该怎样管理它？

传统 Prompt Engineering 主要解决「怎么说清楚一次任务」。Context Engineering 主要解决「给模型哪些背景」。Harness Engineering 进一步上升到「如何设计一个可运行、可控制、可观测、可演进的 Agent 工作系统」。

所以，Harness 的本质不是一段 prompt，而是一套围绕模型的生产系统。它像工程里的脚手架、运行时、CI/CD、权限系统和观测平台的组合体，把非确定性的模型输出接入确定性的工程世界。

## 为什么需要 Harness

文章给出的核心原因是：Agent 从「应答机器」变成「执行主体」后，风险面完全变了。

过去模型答错了，最多是文本不准确。现在 Agent 如果接了文件系统、数据库、CI、发布平台、浏览器、接口平台，就可能写错代码、删错文件、泄露密钥、无限循环、重复调用接口、污染状态。此时只靠「请你小心一点」这种软约束是不够的，必须把规则做进系统。

文章用 R.E.S.T 概括 Agent 系统的四个生产目标：

- Reliability：任务可恢复，关键操作幂等，相同输入下行为尽量稳定。
- Efficiency：Token、API 调用、CPU 时间、延迟和吞吐都要可控。
- Security：最小权限、沙盒执行、输入输出过滤、注入防御。
- Traceability：日志、指标、追踪、决策依据、历史状态都能审计。

这里的重点是：Agent 的可靠性不是靠模型「自觉」获得的，而是靠外部机制逼近的。比如失败后从检查点恢复、工具调用前做权限校验、写操作要求幂等、所有行动留审计日志，这些都是 Harness 的职责。

## 核心框架：PPAF 闭环

文章把 Agent 的运行抽象成 PPAF：

- Perception：感知。把用户输入、工具结果、系统状态、历史记录、外部 API 数据等转成模型能理解的上下文。
- Planning：规划。模型基于当前状态拆解任务、选择路径、分配资源和决定下一步。
- Action：行动。调用工具、执行代码、修改文件、查询接口、回复用户。
- Feedback / Reflection：反馈与反思。把行动结果、异常、指标、验证结论重新注入上下文，推动下一轮规划。

这个循环看起来像「观察 -> 思考 -> 行动」，但生产环境里绝不是简单的 `while true`。它通常需要状态机或工作流引擎支持暂停、恢复、重试、超时、并发事件处理和长周期任务管理。

## 四个工程维度

文章图中把 Harness 拆成四个维度，很值得记：

| 维度 | 核心隐喻 | 工程职责 | 对应 PPAF |
| --- | --- | --- | --- |
| 造缰 | Making the Reins | 定义接口、协议、约束、输入输出边界 | 感知 |
| 驭马 | Riding the Horse | 策略、调度、执行控制、工具路由 | 规划与行动 |
| 相马 | Evaluating the Horse | 评估、观测、选择机制 | 反思 |
| 育马 | Breeding the Horse | 数据回流、训练迭代、记忆体系 | 反思与记忆 |

这四个维度其实对应了 Agent 工程化的完整生命周期：

- 先让 Agent 看见正确的信息。
- 再让 Agent 能安全地行动。
- 然后判断行动是否正确。
- 最后把经验沉淀回系统，让同类错误越来越少。

这也是文章最关键的观点之一：当 Agent 犯错时，好的工程反应不是「换个更长的 prompt」，而是追问系统里缺了什么约束、工具、上下文、验证或反馈机制。

## 战略矩阵：Agent 能力由两条轴决定

文章用一个二维矩阵分析 Agent 应用：

- 横轴：认知循环，从被动响应到主动规划与反思。
- 纵轴：上下文效率，从人工/单点投喂到沙盒化/全自动注入。

四个象限可以这样理解：

- 基础问答与单点工具：低上下文效率 + 被动响应。典型如客服机器人、简单 API 包装。
- 高阶流程自动化：低上下文效率 + 主动规划。能做多步流程，但容易卡在上下文不足。
- 专家辅助系统：高上下文效率 + 被动响应。典型如 IDE Copilot、BI 助手、交互式设计工具。
- 自主智能体：高上下文效率 + 主动规划。典型如自动化代码生成修复、无人值守实验平台、市场分析与交易系统。

这个矩阵的启发是：提升 Agent 能力不能只盯着模型推理，而要同时提升上下文自动获取能力和认知循环能力。只会规划但拿不到真实状态，会空转；能拿到很多上下文但不会长期规划，只能做助手。

## 顶层抽象：Harness 是带边界控制的 REPL 容器

文章把 Harness 抽象成一个带边界控制、工具路由和确定性反馈的 REPL 容器：

- Read：上下文管理器把外部世界和内部记忆翻译成结构化 Prompt。
- Eval：调用拦截器捕获模型的工具调用意图，做路由、权限、超时、配额和错误捕获。
- Print：反馈汇编器把工具结果或异常转成结构化观测结果。
- Loop：持续循环直到任务完成或触发终止条件。

这个比喻很好，因为它抓住了 LLM 与工程系统之间的本质矛盾：模型本身是不稳定、概率化、无状态的；工程系统需要确定、可复现、有状态。Harness 就是中间的翻译层和控制层。

## 最重要的架构原则：状态分离

文章明确指出：要把 LLM 看成无状态计算单元，把跨轮次一致性状态放在 Harness 控制的外部系统里。

这点非常关键。反模式是指望模型在长对话里自己记住任务进度、文件变更、用户偏好、已完成步骤和失败原因。这样做会导致状态漂移、难以调试、行为不可预测。

更稳健的设计是：

- 会话状态放在状态存储里。
- 任务进度放在任务引擎或执行计划里。
- 工具结果进入结构化 observation。
- 长期知识进入文档、向量库、知识图谱或 repo 内文件。
- Prompt 只承载本轮决策必需的上下文。

模型负责「当前这一步怎么判断」，Harness 负责「系统事实是什么」。

## Token 转化：把注意力管理变成工程问题

文章将上下文管理描述为从「无限状态」到「有限 Token」的压缩和映射。这个说法很准确。

Agent 需要的信息可能来自 PRD、TD、接口文档、代码仓库、历史对话、测试结果、日志、监控、知识库、用户偏好。但模型上下文窗口有限，注意力也有限，所以 Harness 需要定义规约规则：

- 哪些信息永远保留。
- 哪些信息可摘要。
- 哪些信息按相关性排序。
- 哪些信息过期后丢弃。
- 外部检索结果注入到 Prompt 的哪个位置。
- 不同信息类型占多少 Token 预算。

这比「把所有资料塞给模型」更重要。文章提到的关键思想是：不要指望模型自己想清楚该关注什么，而要由 Harness 主动构建上下文，把有限窗口留给最有价值的信息。

## Function Calling：文本预测到物理执行的脆弱桥梁

文章把 Function Calling 拆成四步：

1. Schema 序列化：把工具和参数定义注入上下文。
2. 触发生成：模型选择工具并生成参数。
3. 确定性反序列化：Harness 把模型输出转成结构化调用。
4. 观测注入：执行结果返回给模型，进入下一轮循环。

这里最大的风险在第三步和第四步：模型可能生成非法 JSON、参数类型错误、缺少必要字段，工具也可能超时、失败、返回脏数据或产生副作用。

所以稳健 Harness 必须有降级路径：

- 参数反序列化失败时，返回结构化错误并要求重试。
- 参数缺失时，向用户请求补充。
- 工具执行失败时，注入错误细节，让 Agent 反思并重规划。
- 对不可恢复错误快速失败。
- 对外部依赖故障使用退避重试、熔断、降级。

Function Calling 看起来是模型能力，实际上更像系统协议。协议越清晰，Agent 越可控。

## 三大约束与六大原则

文章图中列出 Harness 要面对的三类核心约束：

| 约束 | 现象 | 工程影响 |
| --- | --- | --- |
| 模型能力不完备 | 幻觉、上下文丢失、推理不稳定 | 必须做事实校验、状态维护、行为纠偏 |
| 上下文窗口有限 | 注意力稀释、Token 预算有限 | 必须做上下文规约、排序、压缩和预算分配 |
| 开放环境不可预测 | 工具失效、资源变化、用户干预 | 必须做异常处理、重试、回滚和动态重规划 |

对应的六大设计原则：

- Design for Failure：默认失败会发生，系统要可恢复。
- Contract-First：接口、Schema、事件、API 必须机器可读。
- Secure by Default：安全是默认约束，不是事后补丁。
- Decision vs Execution：规划和执行解耦，模型决定意图，系统执行动作。
- Everything is Measurable：行为、决策、资源消耗都要可度量。
- Data-driven Evolution：每次运行都沉淀数据，用于评测、修复、知识更新。

这些原则可以看成 Agent 系统的工程底座。没有它们，Agent 越强，风险越大。

## 关键工程位点

文章图中列了五个核心工程位点：

| 位点 | 职责 |
| --- | --- |
| Tool Gateway | 工具注册、发现、Schema 提供、权限校验、版本管理 |
| Call Interceptor | 在工具执行前后注入日志、度量、超时、配额、重试、熔断 |
| Feedback Assembler | 把工具原始结果转成模型可理解的结构化观测 |
| Context State Manager | 管理 Token 预算、摘要、RAG、短中长期记忆 |
| Exception Handler | 分类异常，并映射到重试、恢复、降级或上报策略 |

这张图很实用，因为它把 Harness 从概念变成了可建设的模块。如果要从零搭一个 Agent 平台，可以先围绕这五个点设计最小可用版本。

## 实现层面：控制平面与数据平面

成熟 Harness 可以拆成控制平面和数据平面：

- 控制平面：决定做什么。负责任务调度、资源配额、行为规划、策略、权限。
- 数据平面：负责怎么做。承载 Agent 运行实例、状态存储、记忆存储、沙盒执行环境。

文章图中进一步拆成四层：

| 层级 | 控制平面视角 | 数据平面视角 |
| --- | --- | --- |
| L1 呈现与集成层 | API 网关、事件总线、统一入口 | SDK、Webhook、业务产品集成 |
| L2 任务与状态管理层 | 调度器、工作流引擎、长周期任务编排 | 状态存储、任务上下文、检查点 |
| L3 Agent 核心引擎层 | 行为规划器、上下文策略器 | Agent Runtime、短期/长期记忆 |
| L4 执行与治理层 | 策略引擎、资源管理、安全与成本控制 | 沙盒执行框架、工具库 |

这套分层说明 Harness 不是单点组件，而是「AI Gateway + 工作流 + 状态机 + 记忆系统 + 沙盒 + 策略网关 + 观测评测」的组合。

## 记忆分层

文章图中把记忆分为三层：

- L1 感官记忆：Prompt / In-Context 信息。访问最快，但容量小、成本高，只保留当前决策最关键的信息。
- L2 短期/工作记忆：Redis、KV 存储、会话数据库。保存当前任务中间状态和交互历史，用 TTL 和会话粒度治理容量。
- L3 长期记忆：向量库、知识图谱、对象存储。用于沉淀长期知识和复用经验，通常通过 RAG 按需检索。

这对应到实际工程就是：不要把所有东西都塞进 Prompt。Prompt 是工作台，不是仓库。仓库、缓存、索引、摘要和检索系统才是记忆主体。

## 规划模式

文章列了三种规划模式：

| 模式 | 机制 | 优点 | 缺点 | 场景 |
| --- | --- | --- | --- | --- |
| ReAct | 在单个 Prompt 中交替生成思考和行动 | 简单、适合短任务 | 容易迷路或循环，长期规划弱 | 一次性任务、简单工具调用 |
| Plan-and-Execute | 先生成结构化计划，再由执行引擎顺序执行 | 清晰、可审计 | 对环境变化不敏感，需要重规划 | 定时报表、数据流水线、结构化工作流 |
| 分层规划 | 元规划器拆顶层目标，底层 Agent 执行子任务 | 适合复杂项目 | 实现和运维成本高 | 全栈开发、自动科研、大型项目 |

文章建议默认使用 Plan-and-Execute，再按需叠加异常触发重规划和多 Agent 协作。这个建议比较务实：多数企业场景并不需要一上来就做复杂多 Agent，先把计划、执行、反馈、重试做清楚更重要。

## 运行治理：沙盒、安全、成本

Agent 能「动手」后，必须有安全边界。文章给出四级沙盒：

- Level 1 进程级隔离：启动快，适合可信内部工具。
- Level 2 容器级隔离：Docker / containerd，适合多数工具执行。
- Level 3 轻量级虚拟机：Firecracker 等，适合多租户或不可信代码。
- Level 4 完整虚拟机：安全最高但成本最大，只用于特殊高风险任务。

推荐策略是默认容器级隔离，对不可信代码或高敏感数据使用轻量虚拟机加强。

成本治理方面，文章强调：

- Token、API 次数、CPU 时间都要做预算和配额。
- 所有网络请求和工具执行都要有超时。
- 临时错误退避重试，永久错误快速失败。
- 下游依赖连续失败时熔断。
- 关键能力不可用时降级为「弱但安全」模式。

安全治理方面，策略门控位于「规划器 -> 执行层」之间，每次行动前做权限、敏感数据、注入风险和审计检查。

## 度量与演进

文章最后强调，评测指标不是为了做报表，而是反向驱动 Harness 迭代。

核心指标包括：

- 任务成功率。
- 指令遵循度。
- 工具使用有效性。
- 端到端延迟。
- 首次行动延迟。
- 错误率。
- 平均 Token 消耗。
- 平均工具调用次数。
- 策略拒绝率。
- 安全事件数。

指标背后的判断逻辑是：

- 成功率低，回看规划器、上下文策略和工具能力。
- 成本高，回看 Token 规约、工具调用次数和重试策略。
- 错误率高，回看沙盒、外部依赖、超时、熔断和异常分类。
- 安全拒绝多，回看权限模型和任务拆分。

## 我的解读：Harness 是 AI 时代的新型工程平台

这篇文章最有价值的地方，是把很多零散实践统一到了一个框架下：

- Prompt 是局部指令。
- Context 是信息供给。
- Tool 是行动能力。
- Sandbox 是安全边界。
- Memory 是状态与经验。
- Eval 是质量反馈。
- Policy 是治理规则。
- Observability 是可追溯性。

这些东西合起来，才是 Harness。

因此，Harness Engineering 更像平台工程，而不是模型工程。它关心的不是「模型有没有智慧」，而是「组织能不能把模型变成可复用、可管理、可审计的生产力」。

它对工程师角色的改变也很明显：

- 过去写代码，未来更多写规则、契约、测试、文档和自动化反馈。
- 过去调函数，未来更多调上下文、工具链、状态机和评测体系。
- 过去修一次 bug，未来要把 bug 变成系统约束，避免同类问题再出现。

OpenAI 的实验也印证了这一点：三人团队让 Codex 生成百万行级别代码，核心不是「模型替代了工程师」，而是工程师把工作转移到了环境设计、反馈回路、仓库知识、架构约束和自动验证上。

## 对这篇文章的保留意见

这篇文章框架完整，但也有几点需要谨慎理解：

1. Harness 不是新银弹。文章自己也强调，它更多是现有工程实践的新命名。不要因为概念新就把所有问题都包装成 Harness。

2. 概念覆盖面很大，落地时要收敛。文章从上下文、工具、状态、沙盒、安全、成本、评测讲到训练迭代，范围很广。真正做项目时应先抓最小闭环：输入规范、工具网关、执行沙盒、结果验证、日志追踪。

3. 有些能力会被模型内化。随着模型变强，一部分外部 Harness 可能会变薄，比如更稳的工具调用、更长上下文、更强自我纠错。但企业规则、权限、安全、审计、业务状态这些东西依然必须在外部系统中维护。

4. 文章偏框架，案例不够细。如果要落地，还需要补充具体数据结构、状态机设计、工具 Schema 规范、异常分类表、评测集设计和权限模型。

## 迁移到「生码/AI 提效」场景

如果把这篇文章落到前端生码或研发提效，可以这样设计 Harness：

### 输入层

把输入从自然语言变成结构化任务包：

- PRD 链接。
- 后端 TD 链接。
- 前端 TD 链接。
- YAPI / API 文档。
- 固定模板、模板代码或无模板。
- 目标页面、路由、权限、埋点、兼容范围。
- 验收标准和不可做事项。

### 上下文层

让 Agent 不靠人工复制粘贴，而是自动拿上下文：

- 读取仓库结构和现有页面范式。
- 检索组件库文档和示例。
- 解析 YAPI 生成类型和请求方法。
- 读取 PRD/TD 并抽取页面状态、接口、字段、交互规则。
- 通过 `AGENTS.md` 或项目文档提供工程规范入口。

### 工具层

提供稳定工具网关：

- Git / 分支 / worktree。
- 组件文档查询。
- YAPI 查询与类型生成。
- 本地 lint、typecheck、unit test、e2e。
- 截图验证或视觉回归。
- CR Shift-Left 审查。
- Confluence/Jira/需求文档读取。

### 执行层

把执行放进可控环境：

- 每个任务独立分支或 worktree。
- 命令超时和资源配额。
- 写文件范围限制。
- 接口变更必须基于 Schema。
- 高风险操作需要人工确认。

### 反馈层

把结果验证自动化：

- 代码能否编译。
- 类型是否通过。
- 组件是否按规范使用。
- 接口字段是否匹配。
- 页面关键状态是否可截图验证。
- CR 规则是否命中。
- 是否生成任务总结和变更说明。

### 度量层

用数据判断 AI 提效是否真实：

- 单任务完成时长。
- 人工返工次数。
- PR 通过率。
- 代码审查问题数。
- 生码后缺陷率。
- 平均 Token 成本。
- 工具调用失败率。
- 接口契约不匹配次数。

这就是把「让 AI 写代码」升级成「让 AI 在工程系统里交付代码」。

## 可执行总结

如果要从这篇文章里带走一套行动方案，可以按这个顺序建设：

1. 先定义任务输入契约：PRD、TD、接口、模板、验收标准必须结构化。
2. 再建设上下文规约：哪些上下文自动注入，哪些按需检索，哪些摘要保留。
3. 建工具网关：所有工具有 Schema、权限、版本和审计。
4. 建执行沙盒：隔离文件系统、命令、网络和敏感权限。
5. 建反馈回路：测试、lint、类型检查、截图、CR、日志都要进入 observation。
6. 建状态与记忆：任务进度、失败原因、历史决策、已知问题外部化存储。
7. 建指标体系：用成功率、成本、错误率、安全事件来驱动下一轮优化。

最终目标不是让 Agent 永远不犯错，而是让每次犯错都能变成系统改进：补一条规则、加一个测试、完善一个工具、更新一份文档、沉淀一个评测样本。

这就是 Harness Engineering 真正的工程价值。
